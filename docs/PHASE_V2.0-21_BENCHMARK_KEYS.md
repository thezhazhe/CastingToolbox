## 1. 这一阶段解决什么

PHASE V2.0-20 发现：基准表 `data/riser-benchmark/` 的字段能覆盖 131.txt 要的八类信息，
但 **`input_parameters` 的键表只登记了 7 个键，而 `runRiser` 实际读 12 个**。
后果很具体：**用剩下 5 条输入路径产生的案例，按表里的键写下来也算不回原值** ——
而"能复现"是这张表存在的**唯一理由**（README §E：不复现输入，计算结果就没有对照价值）。

本阶段把那 5 个键补齐，并把"补齐"这件事做成**可回归的检查**，而不是一次性的文字修改。

## 2. 任务 A · 参数键表 7 → 12

### 2.1 键名**不是**照抄 V2.0-20 报告，是从代码抽出来的

132.txt §三.1 要求"逐项对照当前真实代码"。做法是**从 `calcs/riser.js` 的注释剥离后源码**里
抽取 `input.X` / `v.X`（`v` 是 `calcMc` 的形参），再与 README 键表做**集合比对**：

```
代码自带 12 个：cast_a / cast_v / cast_wt / eff / hd_ratio / hot_d / mat / mc / mc_mode / rho / shape / wall_t
```

**与 V2.0-20 报告的 12 个一致，无差异。** 报告里点名的 5 个（`hot_d` / `wall_t` / `cast_v` / `cast_a` / `rho`）确认属实。

> ⚠ 为什么必须"剥离注释后再抽"：`riser.js` 的注释里**大量出现** `input.rho` / `v.cast_a`
> 这类字样（那些注释正是在解释这些参数）。不剥注释，抽出来的东西里混着文档而非代码。
> 剥离器**尊重字符串字面量**（`'http://x'` 里的 `//` 不会被当成行注释），这条有自测。

单位取自**界面上的实际单位标记**与代码语义，不是从字段名猜的：

### 2.3 ★ 补齐过程中**新发现**的四处（V2.0-20 没提到的）

这四处都不是"补个键名"能解决的，是**记录时会真的写错**的地方：

**① `eff` 的缺省值按 `shape` 取，不按 `mat`** —— README §3.2

| shape | effKey | 表值 |
|---|---|---|
| `cyl` / `square` | `eff_open` | 14 % |
| `sphere` | `eff_blind` | 20 % |
| `sphere_head` | `eff_sph` | 25 % |

另一个表值 `eff_heat`（发热保温，35%）**不是任何形状的缺省**。
★ 而且独立计算器界面有**四个**效率输入框，**只有与当前形状对应的那一个进入计算** ——
改别的框不影响结果。记案例时若把"界面上的数字"当成"实际用的数字"，就会记错。

**② `mc` 一族走**宽松**解析，与其余键不同** —— README §3.3

- `mc` / `hot_d` / `wall_t` / `cast_v` / `cast_a` 由 `calcMc` 用 `parseFloat` 读取：
  **尾部垃圾被静默忽略** —— `mc='12mm'` 实测得到 **12**；**空串得到 0（算不出冒口），不是"未提供"**。
- 其余键（`hd_ratio` / `eff` / `cast_wt` / `rho`）用 `readNum` 的 `Number(s)`：**严格**，
  `'12mm'` 直接判非法，**空串算"未提供"（用默认值）**。

⇒ **记录时必须写纯数字**。`mc=5.2` 而不是 `mc=5.2mm`。

**③ 三个入口实际送进来的键**不一样** —— README §3.4

| 入口 | 实际入参 |
|---|---|
| 设计中心 `calcManifest.js` | `mat, cast_wt, mc_mode='direct', mc, shape, hd_ratio=1.0(硬编码), eff=undefined, rho?` |
| 独立计算器 `riserView.js` | 除 `rho` 外的 11 个（`eff` **总是显式传**） |
| 向导 `wizard.js` | `mat, cast_wt, mc_mode='direct', mc, shape, hd_ratio, eff=undefined` |

★ **向导把三种 Mc 方式在界面内先换算成 `mc`，再统一按 `direct` 传**
（`wizard.js:432-437`；`wz_hot` 输入框在 `:322` 已 `/2`）。
⇒ 从向导来的案例，**`hot_d` / `wall_t` 不会出现在入参里**。
记 `input_parameters` 要写"实际送进 `runRiser` 的那一组"，不是"界面上填过的那一组"。

**④ `mat` 写错不拒算，只回退** —— 回退球铁 + 标记 `mdFallBack`。
一条材料写错的案例**照样能算出数**，只是用的是球铁的密度与收缩率。记案例时要注意。

### 2.4 ★ 一处**没有改**的地方（有意保留）

`cast_wt` 的 `NaN` **不算"未提供"，它会拒算**。这是 V2.0-18 的有意设计：
`cast_wt` 的缺省值本身就会关掉整条体积校核，若把 `NaN` 也算"未提供"，
等于绕个弯把"意外关闭体积校核"重新放进来。
⇒ README 明确写：**要表示"不做体积校核"，写 `cast_wt=0`。**

### 3.5 ★ 两个测试自身的 bug（被测试自己抓出来）

- **E2 第一版**用 `src.length` 当"字节数"断言 ⇒ 实测 14,094 ≠ 19,958。
  原因：`readFileSync(f,'utf8')` 返回**字符串**，`.length` 是 **UTF-16 码元数**；
  文件是 **19,958 字节**（中文注释 3 字节/字）。**改成真 sha256 指纹**（也是项目一贯口径）。
- **B3** 断言原型链探针 ≥10，实际 8 —— 过滤器只匹配 `constructor|__proto__|toString|hasOwnProperty`
  四个词，6 键 × 2 路径中命中的就是 8。**是断言写错，不是探针少。**

### 3.6 ★ 顺带修的一处 README 缺陷

README §7 原来给了一条 `split(',')` 数列数的一行命令。**它在真实数据上会算错**：
Excel 给含逗号的单元格自动加引号，`split(',')` 会把 `"壁厚 8, 热节在下部"` 拆成两格
⇒ 列数报错，而它看起来"只是多了一列"。
**改为指向校验脚本**（用能处理引号的 CSV 解析），并加测试 `C4` 钉住那条一行命令不再出现。

## 4. 任务 C · 案例证据分级说明

README §4 改名「可信度与证据等级」，新增：

**§4.1 等级速览**（132.txt §五 的三档，与本表 `evidence_level` 的对应关系）：

| 等级 | 一句话 | 必备 |
|---|---|---|
| **L1** | 关键输入 + 实际冒口尺寸 + 生产记录 + **可靠检测结果**，四样齐全 | 有检测报告/解剖记录，`source` 能查到原件 |
| **L2** | 有**部分真实工艺数据**，但**缺检测结果或其他关键证据** | 有生产文件，无专门缺陷检测 |
| **L3** | **参考性历史资料或不完整数据** | 口述/回忆，无书面原件 |
| （L4） | **推测** —— 允许录入，只能当线索 | 内容写成 `推测:` |

★ **L1 的定义被收紧**（原来只说"有检测报告/解剖记录"）。
现在要求**四样齐全**，缺任何一样降到 L2。
只有检测结论、却不知道当时用的 `Mc` 或实际冒口尺寸的，**不算 L1**。
（收紧方向符合项目纪律"只能变强不能放宽"；表里 0 条记录，无既有记录因此改变等级。）

**§4.2 四条硬规则**（132.txt §五 要求的四条，逐字落到 README）：

1. **人工参数扫描和模拟数据不得计入真实铸件验证数量。** 内部实验的出处是 `tests/experiments/`，
   与本表**分开统计，不得相加**。（这条正是 V2.0-20 那 212 组样本的教训。）
2. **同一铸件的多个热结不能未经区分地视为多个独立铸件案例。**
   一个件 3 个热结 = **1 个**案例；要分热结记必须在 `case_id` 上体现同源（`-01a/-01b`）。
3. **缺陷位置是事实记录，不是缺陷原因结论。** "缩孔在冒口颈下方"是**观察**；
   "因为冒口太小所以缩孔"是**判断**，必须写 `推测:` 并标 L4。
4. **只有满足相应证据要求的案例才能支持对应级别的工程结论。**

> ⚠ **没有新增任何 CSV 列，也没有重构多热结数据结构**（132.txt §五 明令）。多热结只给了
> `case_id` 后缀这一条**不动结构**的约定。
