## 4. GT 真值定义（命令文件 §三）

### 4.1 坐标怎么来的

**全部由生成器 `gen_engineering.mjs` 内的几何参数**解析**算出，在跑 V3 之前写进 `expected.json`**
（文件头第 5-7 行明文纪律："GT 全部由独立几何参数解析计算……禁止根据 V3 结果反推/修改 GT"）。

典型写法（`gen_engineering.mjs:82-90`，t01）：

```js
const pl = [500, 500, 20], bs = [200, 200, 100];
const pz = pl[2] / 2, bossC = [0, 0, pz + bs[2] / 2];   // ← 板顶 + 凸台半高 = 凸台盒中心
...
expectedHotspots: [{ thickZoneId: 'boss', positionMm: bossC, toleranceMm: 40, rank: 1 }],
```

**不是**人工指定、**不是**最大厚度中心、**不是**公式算出的凝固点——就是**解析基本体的几何中心**。

### 4.2 语义是什么

**统一回答：A. 几何意义上的"厚区中心"。**

- box 型：`centerMm` = 盒体中心（凸台从板顶起算的几何中心）
- ring 型：`centerMm` = 环带中心，匹配用**径向带 [innerR, outerR] + 轴向 |Δ| ≤ halfH**，误差取"到中径的偏离"
  （`run_engineering.mjs:45-57`）
- **没有任何一个模型**用"理论最后凝固点""缩孔位置""feeder feeding hotspot"语义

### 4.3 语义并非完全统一——必须指出

| 模型 | 特例 |
|---|---|
| **t08 / t19 / t20-topFlange** | GT 是 **ring 型**，用环带匹配而非点距离。**同一模型内混用两种匹配**（t19 的 `stub` 用点、三个法兰用环带） |
| **t06_taperStairs** | `positionMm = thickEnd`（阶梯的**厚端中心**，`gen_engineering.mjs:204`），不是整体中心 |
| **t15_weakRamp** | 容差 **25mm**（全场最严），其余是 30/35/40/45 |

### 4.4 判定规则（`run_engineering.mjs:63-103`）——**这条最关键**

```
pass = 漏检数 == 0 && 误报数 == 0 && 排序正确
匹配 = 贪心：按 V3 输出顺序（已按 M 降序），逐个找最近的「未被占用」expected
      距离 ≤ toleranceMm → 配对；否则 → 记为 falsePositive
```

**由此推出一条必须写明的性质**：

> **任何位置超出容差球的真实热点，都会被计成"误报"（false positive）。**
> 这套判据测的是**位置精度**（点是否落在厚区中心的容差球内），**不是检测能力**。
> 一次位置超差会**同时**产生"1 个漏检 + 1 个误报"——t03/t04 的"漏 2 误报 2"听起来像四个问题，
> **实际只是两个点各偏了一次**。

### 5.2 逐条回答

**Q1. peak 是否比 representativePoint 更接近工程上定义的热点？**

- 就"靠近生成器声明的厚区几何中心"而言：**是**。峰→GT **11.6 mm**；代表点→GT **45.4 mm**。
- 但"更接近 GT"**不等于**"更接近物理热节"——GT 本身就是几何量（§4.2）。这一问需要在 §5.3 分开判。

**Q2. boss/base interface 是否具有更大的 V/A / modulus？**

**两种口径给出完全相反的答案 —— 这正是全部矛盾的根源：**

| 口径 | 交界带 (z=11.1) | 凸台中段 (z=48.6) | 谁大 |
|---|---|---|---|
| **封顶 M**（= 引擎报告的 `peakModulus`） | 7.03 | **14.42** | **凸台中段大 2×** |
| **未封顶原始 V/A**（= region 生长判据） | **25.89** | 14.42 | **交界带大 1.8×** |

**同一个物理量、同一套代码，两种口径给出相反结论。**

**Q3. 如果 interface 的 modulus 更高，它是否理论上应被视为最后凝固区域？**

**分口径回答，且必须由工程判断定夺：**

- 按**未封顶 V/A**（交界带 25.89 最高）：交界带"看起来"最厚——但这是**窗口效应**：
  交界处的采样窗口同时框住了凸台和底板，V 大而 A 小，V/A 被推高。**它反映的是"窗口里有多少料"，
  不是"这个散热体有多大"。**
- 按**封顶 M**（中段 14.42 最高）：`modulusField.js:72` 用 `M ≤ (1/3)×d`（d = 到最近表面距离）
  压制。**这是 Chvorinov 意义上的模数**——模数是"整个散热体"的 V/A，不是局部窗口的 V/A。
  从中段到顶端 M 单调下降、到交界急降，符合"凸台的热心在中段"这一经典认识。
- **从冒口设计角度讲，交界处确实是补缩困难区（几何热节）**——但这属于"要不要为交界单独设冒口"的
  工艺判断，**不等于"engine 报的代表点就该落在交界上"**。

**Q4. 当前 representativePoint 为什么会从 boss 中心向 base/interface 移动？**

**已定位到确切代码与确切数字，不是猜测。** `peakRegion.js:118-146`：

```js
const peakRaw = field && field.A[peakPt] > 1e-9 ? field.V[peakPt] / field.A[peakPt] : 0;
const threshold = Math.max(peakM, peakRaw) * o.regionGrowRatio;   // 0.8 × max(封顶M, 未封顶)
const rawOf = (t) => (field && field.A[t] > 1e-9 ? field.V[t] / field.A[t] : M[t]);  // 成员判据 = 未封顶
```

- **峰用封顶 M，region 生长用未封顶 V/A —— 两把尺子。**
- t03 的阈值 = 0.8 × max(14.42, 14.42) = **11.54**
- 交界带 raw = **25.89 ≥ 11.54 ✓ 进区**；板内 raw = **14.06 ≥ 11.54 ✓ 也进区**
- 于是 region 从中段**一路向下长**（z 范围 −7.7 ~ 104.8），质心被拽到 z = 14.8

**Q5. 这属于哪一类？**

> **"V/A 定义造成的合理结果" + "region growth 判据口径与峰值口径不一致"。**
> **不是**算法算错（峰点位置是对的，M 值是对的），**也不是**GT 定义过于理想化（GT 从没声称自己是凝固点）。

——**"测试未预期" ≠ "工程上错误"**，这条在数据上成立；但**也不能反过来把所有误报都说成判据问题**，
11 个厚区外的偏移是实打实的。

## 8. representativePoint 的工程意义（命令文件 §七）

当前实现（`peakRegion.js:177-181`）：

```js
export function representativePoint(geometry, sample, region) {
  const c = region.centroid;
  if (isInside(geometry, c, 6)) return c;     // 合法 → 用质心
  return sample.pts[region.pts[0]];           // 不合法 → 回落峰点
}
```

| 问题 | 回答 |
|---|---|
| 1. centroid 对**长条形**热结合理吗？ | **偏差最大**。长条区域质心会被长度方向拉向几何中心，远离最热端；且长条区域生长更易顺着结构蔓延（t07 偏心块、t20 basePad 都是这类） |
| 2. centroid 对 **boss + base 组成**的区域合理吗？ | **不合理**（§5.2 Q4 已实测）。两个不同散热条件的结构被当成一个连通域，质心落在两者之间，**既不是凸台中心、也不是交界** |
| 3. centroid 是否天然被"大体积区域"拉偏？ | **是**。region 体积现行是旧口径的 11~139 倍（§5.3），体积越大质心越受远端牵连 |
| 4. peak 是否更接近"最热位置"？ | **是**。peak 是 `M = V/A` 的极大点，M 是 Chvorinov 意义上的凝固时间尺度；本套件里峰→GT 距离普遍只有代表点的 1/3~1/5 |
| 5. centroid 是否更适合表达"热结区域中心"？ | **是，但前提是区域的划分口径先自洽**。当前区域用未封顶 V/A 生长，与封顶 M 的峰值不是同一把尺子（§5.2 Q4） |

**对下游用途分别需要哪一种：**

| 用途 | 需要什么 | 理由 |
|---|---|---|
| **冒口定位** | **A. peak point**（或 peak 加权） | 冒口要坐在**最后凝固**的位置，那是 M 极大点，不是区域几何中心。**当前给的是质心，这是个真问题** |
| **冷铁定位** | **D. hotspot region**（整个区域） | 冷铁要覆盖的是**面/区域**，不是点；区域边界比质心更有用 |
| **工艺检验** | **D. region + A. peak**（两样都要） | 检验既要"哪块厚"（区域/体积），也要"最厚在哪"（峰点）。**只给质心最没用** |
| 3D 显示 | B. centroid 可接受 | 标记要落在热结"看着像"的位置，质心视觉上合理 |

**本阶段只做分析，不改算法**（命令文件 §七 明示）。

## 9. adaptive sampling 审计（命令文件 §八）

### 9.1 确认的事实（逐条对照命令文件的清单）

| 项 | 实测/代码确认 |
|---|---|
| bbox 最大尺寸 | `mdim = max(bounds.size)`，**只用最大维**，三轴共用同一个 vs |
| coarse grid 16~128 | 探测阶梯 `probeResolutionSteps=[16,32,48,64,96,128]`；**最终主网格可到 256**（`maxSampleGs`） |
| characteristic distance | `char(p) = 2 × BVH 最近表面距离` |
| char < 2mm filter | ✅ `charFilterMin = 2`（网格化曲面伪曲率） |
| p10 wall estimate | `estMinWall = chars[p10]`，**保底 `max(estMinWall, 4mm)`** |
| target voxel size | `vs = clamp(0.5 × estMinWall, mdim/128, mdim/24)` |
| 256/axis 上限 | ✅ `maxSampleGs = 256` 硬夹 |
| 最多 3 levels × 2 phases | ✅ `sampleVsLevels = 3`，每级原相位 + 半格偏移 |
| internal points ≥ 128 停止 | ✅ `minInsidePoints = 128` |
| **triangle count** | **完全不参与**（`adaptiveVs` 签名里就没有它） |

### 9.2 20 个模型的实测（证明"triCount 不参与"）

| 模型 | triCount | bbox 主维 | vs (mm) | 每轴格数 | estMinWall |
|---|---|---|---|---|---|
| t06_taperStairs | 151,120 | 300 | **2.34** | 128 | 4.00 |
| t13_farPair | **223,184** | 1000 | **7.81** | 128 | 12.50 |
| t14_taperSeries | **360,160** | 1200 | **9.38** | 128 | 15.00 |
| t02_thin10_boss60 | 187,296 | 500 | **10.79** | **46** | 21.57 |
| t17_weak_30_60 | 113,216 | 500 | **14.38** | **35** | 28.75 |
| t10_multiDirBoss | 94,872 | 504 | 9.38 | 54 | 18.75 |

**面数从 9.5 万到 36 万（3.8×），vs 与格数完全不受影响** —— vs 由 `mdim` 与 `estMinWall` 决定。

### 9.3 "用户所谓的'采样率低'"到底指什么

对照命令文件给的 A~G 选项，**逐条判定**：

| 选项 | 判定 | 依据 |
|---|---|---|
| A. 网格数量低 | **❌ 不是** | 每轴格数落在 35~129，128 是设计上限；10/20 个模型就在 128 |
| **B. 局部薄壁特征没有采到** | **✅ 是——这正是 UI 说的那个** | UI 的"采样不足/精度低"chip 由 `thinFrac = P(t < 2×vs) ≥ 0.10` 与 `bodyLayers < 2` 驱动，**与格数无关** |
| C. hotspot 空间分辨率不够 | ⚠️ 部分 | `refineMinRes=16`、`refineMaxPoints=8000` 是细化层的独立上限 |
| **D. triangle 很多但采样仍然不密** | **✅ 是，且常见** | t13 22 万面 vs=7.81；t06 15 万面 vs=2.34 —— **面数与密度无关** |
| **E. STL 尺寸太大导致 voxel 变大** | **✅ 是** | `vs = clamp(..., mdim/128, mdim/24)`：mdim=1200 的 t14，vs 下限就是 9.38mm，永远细不过这个数 |
| **F. 局部几何尺度小于最终 vs** | **✅ 是**（= B 的成因） | t14 的 40mm 厚端 vs=9.38 → 只 4 层 |
| **G. 其他** | **✅ 有一条** | **`estMinWall` 被 `estWallFloor = 4mm` 保底 —— 20 个模型里 8 个命中保底值 4.00**，即 vs 由保底值而非真实壁厚决定（`configV3.js:16` 自注"工程假设 UNKNOWN，待真实 STL 校准"） |

**汇总结论**：用户感知的"采样率低"**不是"网格格数少"**，而是 **B/D/E/F** ——
**模型越大、局部特征越小于最终 vs，采样就越不够**。这是**尺度相关的固有行为**，不是 bug。

**本阶段未修改 sampling**（命令文件 §八 明示）。也未新增诊断输出（无必要：`debug.coarse`
已有 gs/vs/estMinWall/thinFrac，`thin.tP10/tP50` 也在）。

### 10.3 coplanar overlap —— 按命令要求"只记录，不实现"

## 11. 当前真正的问题是什么（回答 A~E）

**A. 当前算法是真的明显错误？**

**不是"算错"，是"内部口径不一致"。** 实测证据：

- 峰点位置**是准的**：t03 峰→GT 11.6mm、t04 10.5/11.1mm、t18-H4 5.3mm
- M 的数值**是自洽的**（置信度四因子公式逐项复算完全吻合）
- **但**：峰值用**封顶 M**、region 生长用**未封顶 V/A**，两把尺子（§5.2 Q4）。
  结果是区域把质心拽到交界/板内，而 `representativePoint` 直接返回质心。
- 归类：**是真实存在的问题**，但属于**定义/一致性问题**，不是数值算错。

**B. 还是测试的 GT 坐标/判定标准过于几何化？**

**两者都成立，且必须分开看。** 数据：

- **19 个误报里 8 个落在生成器自己声明的厚区几何体内**（§7）→ 判据确实过窄（8/19）
- 判据测的是**位置精度**（到厚区中心的容差球），不是检测能力（§4.4）→ 会把
  "检出了但点偏"记成"漏检 + 误报"
- 但 **5 个峰点级偏移（A 类）** 与 **11 个落在厚区之外的误报**，**不能**用"GT 太几何化"解释
  —— 判据问题**只解释得了一部分（8/19）**，不能全推给测试

**C. 哪些失败属于算法问题？**

- 峰点层 5 个（t06×2、t15-H5、t20×2）——**需进一步定位**，本阶段未追到根因
- region 生长口径不一致（§5.2 Q4）——**是代码内的事实**，是否算"问题"取决于对"热点位置"的定义

**D. 哪些失败属于测试定义问题？**

- **19 个误报里 8 个落在声明厚区几何体内**（5 个峰点还在容差内）→ 这部分是判据未纳入
- **t19 的 stub / midRing**：生成器**自己写明**"弱次级热结 M≈0.4×法兰，置信度 ~0.49 < 0.5 拒
  ——非必报"（`gen_engineering.mjs:558`），**却仍写进 expectedHotspots** → **定义自相矛盾**，
  纯属测试问题
- **t06**：GT 只要 1 个（最厚段），V3 报了 2 个（厚端 + 次厚段）→ GT 未纳入

**E. 下一阶段如果优化，最小、最安全的改动是什么？**

**本轮不建议动算法**（见 §14 路线）。若将来要走算法路线，候选是**一处**：

> 让 region 生长判据与峰值判据**用同一把尺子**（`peakRegion.js:127-130` 一行级改动）。
> **但风险高**：该处正是 PHASE 24 为修 ALR2510 `tiny_region` 漏检而专门改的，
> 改回去会重新引入那个真实件的漏检。**必须先有"代表点该取什么"的工程结论。**

## 14. 下一步建议

### 明确结论

**路线 B：先修改 engineering truth suite 的判定定义，再继续算法优化。**

（命令文件 §十二 限定只能从 A/B/C 中选一个。）

### 为什么不是 A

路线 A（保持算法不变、扩大真实 STL 测试集）**解决不了当前的核心问题**：
现在的 9/20 里，**判断"这 25 个未匹配热点到底是错还是对"本身就没有依据**——
拿真实 STL 去测，同样会遇到"哪个点才算对"的定义问题，只是把问题往后推。

### 为什么不是 C

路线 C（确认存在明确算法问题后做最小修改）**证据还不足**：

- 14/32 的失败，**峰点是对的**（§6.1）→ 这些不是"算法问题"，是"代表点定义"
- 5 个峰点级失败，**本阶段没定位到根因**（§13-1）→ 不满足"确认存在明确算法问题"
- 唯一找到的代码级不一致（region 生长口径）**正是 PHASE 24 为修 ALR2510 漏检而特意引入的**，
  贸然改回会**重新打开一个已关闭的真实件问题**
- 命令文件 §十二 明示"**不要为了'有进展'而强行选择 C**"

### 路线 B 的具体建议（供下一阶段讨论，本阶段不做）

1. **把判据从"到厚区中心的距离"改为分层的两问**：
   - 第一问（检测）：热点是否落在**声明的厚区几何体内**？（现在这一问根本没人问）
   - 第二问（精度）：落点离厚区中心的距离是多少？（只作为精度指标，不参与 pass/fail）
   依据：19 个误报里 **8 个**落在厚区内（其中 5 个连峰点都在容差内）—— 这一问现在被容差球吞掉了。
2. **拆掉"误报"这个词的误导**：把 `falsePositives` 改名为 `unmatched`，
   并区分 `unmatched_in_zone`（检出正确、位置偏）与 `unmatched_out_of_zone`（真·额外检出）。
   依据：§4.4 —— 当前语义把"位置偏"和"多报了"混为一谈。
3. **修掉 t19 的定义自相矛盾**：生成器自己写"stub/midRing 非必报"，却把它们写进了
   `expectedHotspots`（`gen_engineering.mjs:558` vs `:552-557`）。**二选一，不要两边都写。**
4. **补一个"干净网格"对照组**：20/20 都是 `INCONSISTENT_WINDING`，无法量化缠绕影响。
5. **加一条"边界偏移"记录**：把每个热点的 `peak→GT` 与 `representative→GT` **都写进 result.json**
   （现在只存了 representative 与 geometrySource 字符串）。这样"误差发生在哪一层"一眼可见，
