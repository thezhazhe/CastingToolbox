**最小修复**：把被吞掉的两行原样补回（`data/tags.js` 末尾，与 dist 副本逐字一致）。

## B. 工艺检验中心

### B.1 数据模型（§二十七）

```
ProcessInspection
├─ 对象模型      js/model/processInspection.js   多实例容器 / ID 命名 / 关系 / 汇总（纯函数，Node 可测）
├─ 几何度量      js/model/objectMetrics.js       单件 V/A/M/包围盒/主轴/截面积剖面（纯函数，无 three.js）
└─ 视图          js/views/inspectionCenter.js    #/inspection
```

**为什么新算法放在 `js/model/` 而不是 `js/engine/`**：§三 冻结 `js/engine/` 全部 7 个文件，
且 PHASE 87 的收口核验方式就是 `git status -- js/engine/` 无输出。新几何算法放 model 层 →
**引擎目录零改动这条核验依然成立**（见 §D）。

### B.2 多实例（§六 —— 本阶段最重要的设计要求）

从第一行代码起就是 N 个，不是"先做一个，以后再说"：

| 对象 | 基数 | ID |
|---|---|---|
| Product | **1**（§七） | P1 |
| Hotspots | N ≥ 0 | H1…Hn（**引擎给的 id，不重编号**） |
| Risers | N | R1…Rn |
| Sprues | N | S1…Sn |
| Runners | N | G1…Gn |
| Ingates | N | I1…In |

ID 由类别前缀 + 序号生成（`objectId()`）；删除后 `reindex()` 重新编号保证连续。
容器一律是数组，UI 一律是"计数 + 逐项明细"，**没有任何一处假设只有一个**（§十五）。

### B.3 多 Hotspot（§八）

**直接消费 Hotspot V3 的既有输出**：`toViewResult(analyzeHotspotsV3Sliced(...))` ——
与设计中心**同一条链**，没有第二套热结算法。取用字段 `id / x / y / z / mc / regionVolumeCm3 / confidence`。

N ≥ 0 是合法状态：0 个热结不是缺陷（可能是均匀件），汇总条如实说"未检出热结"，**不报错、不冒充**。

### B.4 多冒口与热结 × 冒口关系（§九 / §十一 / §十二 / §十三 / §二十六）

**内部算全 N×N，页面绝不展示矩阵。**

```
buildRelationRows(hotspots, risers)
  → rows[i].all     ：该热结到**全部**冒口的距离/模数/M比，按距离升序
  → rows[i].nearest ：几何最近的冒口（§十三 默认关联规则）
  → counts          ：covered / modulusOk / modulusLow / modulusUnknown
```

- **距离** = 热结代表点与冒口**包围盒中心**的直线距离（中心距）。
  热结坐标用**引擎原值**，不用显示层微调点 —— PHASE 86 的显示拉近是纯展示行为，不参与工程计算。
- **术语纪律（§二十六）**：全程用「**最近冒口**」，代码字段名也是 `nearest`。
  **不出现"负责冒口"** —— 本版没有空间/连通性判据，不做这个判定（UI 有明文说明，测试有断言）。
- **距离不设红线（§十三）**：只计算、只展示，级别恒为 **INFO**。
  测试 `88-判据` 专门断言：距离 99999mm 也不得产生 WARNING。**没有拍脑袋造阈值。**

### B.5 冒口模数检查（§十）

```
M_riser ≥ M_hotspot × 1.2     ⇔     M_riser / M_hotspot ≥ 1.2
```

- `M_riser` = 冒口 STL 自身的 **V/A**（§九）；`M_hotspot` = 引擎的 `peakModulus`。
- `MODULUS_RATIO_MIN = 1.2` 是**具名常量**，判据只此一处，测试锁死边界（1.20 满足 / 1.199 不足）。
- 页面明写：**「模数比为经验性工艺检查指标，不等同于凝固模拟结果」**（§十 末段要求，不包装成物理仿真）。
- 边界情形：冒口 STL 无效 → 模数 `null` → `ok: null`，**既不算满足也不算不足**，
  单独计 `modulusUnknown` 并给 INFO（不把"算不出来"混进"不足"里）。

### B.6 浇注系统（§十五~§二十二）

多 Sprue / 多 Runner / 多 Ingate 全部按 N 处理。每类统计：**数量 / 总体积 / 几何尺寸 / 截面积（可靠才算）**。

**总截面积（§二十）**：

```js
totalMm2: usableAreas.reduce((s, a) => s + a, 0)      // ΣAi —— 定义式，逐个相加
```

**不是** `平均面积 × 数量`。每个内浇口保留独立结果 `Ii → Ai`（`perIngate`），UI 折叠后逐条可查（§二十一）。
测试 `88-E` 用 24 个**故意不等**的面积（72…95）验证 `total === ΣAi`、`min`、`max`、`avg = ΣAi/24` 四项，
并断言 `perIngate.length === 24`。

**浇注系统不建 PASS/FAIL（§二十二）**：只做几何统计 + 汇总 + 数据关系。
现有的浇注比例表（`RATIO_PRESETS`）是**设计输入**不是**校核判据**，故未复用、也未新造标准。

### B.7 截面积：诚实边界（这是本阶段最需要你知道的一件事）

**充型方向对一个孤立的连接体在几何上是不可判定的。**
30×6×8 的内浇口与一段 30×6×8 的横浇道是**同一个实体** —— 没有任何几何量能区分。

实测（`_p88_metrics_probe.mjs`，30 宽 × 8 长 × 6 厚，真实浇口截面应为 30×6 = 180）：

| 基准轴 | 截面积 | 说明 |
|---|---|---|
| 主轴（= 最长边 X） | **48** | ⊥X = 8×6，**与真实浇口面积差 3.75 倍** |
| Z | 240 | ⊥Z = 30×8 |
| **Y（充型方向）** | **180** | ← 正确值 |

因此本模块的三条设计是**必需的，不是过度设计**：

1. 默认 **体积加权主轴**（PCA）—— 对细长件（直浇道、横浇道）正确，实测圆柱 ⌀40×200 主轴精确 = 长轴；
2. 每类允许**显式指定 X / Y / Z**（UI 上一个下拉，改完毫秒级重算）；
3. 结果里**带着"用了哪条轴"**，UI 与明细表都如实展示，**假设不隐藏**。

另外两条护栏：
- 采样带取轴向中段 **20%~80%**（两端是与其他几何相接处，截面畸变）；
- **未闭合环直接拒绝给数**（`closed=false` → `usable=false` → 显示"无法可靠计算"，不猜）。

> 报告中如实记录：`主轴` 对**扁宽内浇口**会低估。UI 提示与 §二十二 的说明都已写明"主轴可能不是充型方向"。

### D.3 本阶段查出并修掉的 4 个真问题

都不是风格问题，都是实打实会误导用户或让功能静默失效的缺陷：

**① 浇注系统整块渲染抛异常（ID 解构错名）**
`renderGating` 里 `const { gating } = d.gating`，而 `d.gating` 就是 `gatingSummary()` 的返回值、
**没有 `gating` 这个键** → `gating.sprue` 抛 TypeError → 该区块保留上一次的旧内容。
表现：导入了内浇口，④ 却仍显示"未导入"，且 ⑥/⑤ 也一并停更。**已修**。

**② 3D 场景在整视图重渲染后消失**
场景指纹只比对"对象集合变没变"。但 `render()` 会整块重写 `container.innerHTML` ——
**换语言、离开视图再回来都会走这条路**，旧 canvas 连同元素一起没了，而对象集合没变 →
误判"无需重建" → 3D 视图直接消失。**已修**（指纹增加"承载元素本身是否换了"），
并**加了回归守卫测试**（⑥.5 段）。

**③ 导入顺序与编号错位（并发竞态）**
每个文件都要 `await file.arrayBuffer()`。连续两次投放若并发解析，**完成顺序可能与投放顺序不一致**，
对象就按完成顺序拿到 R1/R2/R3 —— 实测出现 **`R2 = R3.stl`、`R3 = R2.stl`**。
**已修**（导入串行队列），并**加了回归守卫测试**（断言 `id + '.stl' === filename`）。

**④ 硬编码中文 `= Σ 单个截面积`**（违反 §三十二）。**已修**。

> 这三个"静默失效"型缺陷（①②③）都是**测试抓出来的**，不是看代码看出来的 ——
> 这也是为什么 §二十九 要求的那几个 Case 里，"数量对不对"之外的断言（顺序、重建、折叠态）值得写。
