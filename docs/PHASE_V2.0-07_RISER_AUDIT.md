## 3. Mc 的状态矩阵（`calcManifest.js:191-237`）

```
① 用户勾选了热结（process.hsPick 非空）   → mc = max(勾选热结的 mc)，userMc = true
② 有热结且用户改过 mcHotspot               → mc = 用户值，userMc = true
③ 无热结且用户改过 wallHot                 → mc = 用户值，userMc = true
④ 有热结、未改过                           → mc = process.mcHotspot（STL 自动），note = 06A1 未确认提示
⑤ INSUFFICIENT_RESOLUTION / LOW_CONFIDENCE → blocked，不自动建议
⑥ NO_HOTSPOT                              → mc = wallHot（主体壁厚 ÷ 2），带口径说明
```

> ⚠ **① 这条路径在 `:266-270` 就 return 了**，**不经过** `:277` 的
> `level = (userMc || note) ? 'WARNING_REVIEW' : …`；
> 它的等级由 `:268` 的 `edited`（Mc 是否被改过）单独决定。**这就是 D1。**

## 4. 已确认的缺陷（有实测证据）

### 🔴 D1 —— 勾选热结即可把「未确认的自动 Mc」装扮成已确认输入（**假 ✅**）

**这是一条完整的一键旁路，且产生的是错误的确定性。** 【实测·浏览器】

| 步骤 | 卡片等级 | 06A1 的未确认提示 | D / H | `f` |
|---|---|---|---|---|
| ① 默认（不勾选） | 🟡 需人工复核 | ✔ 在 | **147 / 147** | 1.75 |
| ② **勾选 H1（不改任何数字）** | **✅ 可直接采用** | **✘ 整条消失** | **147 / 147** | 1.75 |
| ③ 勾选 H1 并把 Mc 改成 20 | 🟡 需人工复核 | ✔ 在 | 144 / 144 | 1.20 |

**场景 ② 的卡片上同时出现两句话**（同一次渲染、同一张卡）：

```
来源：STL 热结检测 Mc = 14 mm（最大热结 H1；共 2 个热结） —— 自动估计值，尚未验证适用于所有几何
② 冒口设计  ✅ 可直接采用
```

**机制**【源码确认】：

- `designCenter.js:1339-1353`：勾选框 `change` → `applyPick(id, det)`，`det = h?.mc`（**检出值**），
  写入 `process.hsPick`，标记 `SRC.USER_INPUT / CONF.USER_CONFIRMED`。
- `calcManifest.js:262` `edited = pickedHot.some(p => |p.mc − 检出 mc| > 1e-9)` → **false**（没改值）。
- `calcManifest.js:268` `level: edited ? 'WARNING_REVIEW' : reliabilityLevel({geomStatus, hsStatus})`
  → `reliabilityLevel`（`:515-519`）**只看几何与热结分析状态，不知道 Mc 是不是自动值** → `SAFE_TO_RECOMMEND`。
- 而**单热结路径**（`:277`）恰恰写了这条规则：
  `const level = (userMc || note) ? 'WARNING_REVIEW' : reliabilityLevel(...)`
  上面的注释（`:275-276`）逐字写着「它与 note 必须同一口径，否则一处说"可直接采用"、一处说"未经确认"」。
  **⇒ 规则本身是对的，只是勾选路径没走这一行。**

**加重因素**【源码确认】：`designCenter.js:1431` 的改 Mc 弹窗提示逐字写着
「冒口将按下面填写的模数设计（**默认即检出值，可直接采用**）」——**界面在主动邀请用户接受自动值**。

**影响**：06A1 建立的"未确认不得给确定性结论"在**默认交互路径**上失效；
用户看到 ✅ 会停止复核，而那个 ✅ 描述的是一个**未经任何验证的自动估计值**。

> 探针说明：真实 STL 导入走的是完整链路（`cube50.stl` → 引擎 → 项目），
> 热结条目与铸件重量按 `browser_p78_test.mjs` 的既有手法**播撒**进项目
> （为了控制"重件 + 2 个热结"这个场景，真实 cube50 无热结）。
> **这不影响结论**：D1 的机制在源码里是确定的（`:268` vs `:277` 两条不相交的分支），
> 播撒只决定 `Mc`/`cast_wt` 的取值，不决定走哪条分支。

### 🟠 D2 —— 勾选路径的「来源」行把用户输入标成 STL 自动值

【实测·浏览器】场景 ③（用户把 Mc 改成 20）卡片显示：
`来源：STL 热结检测 Mc = 20 mm（最大热结 H1；共 2 个热结） —— 自动估计值，尚未验证适用于所有几何`

`20` 是**用户输入的**，不是 STL 检测的。**机制**【源码确认】：
`resultsCenter.js:42` 的 `mcSourceLine` 读 `ctx.mcUser`（`:460` = `process.mcHotspot.src`），
而勾选路径改的是 `process.hsPick[].mc`，`mcHotspot.src` 仍是 `STL_GEOMETRY_ANALYSIS`
⇒ **同一张卡上"用户确认的 Mc"被标成"自动估计值"**（与 D1 方向相反的错标）。

### 🟠 D3 —— 体积校核主导时，用户"确认 Mc"不改变任何尺寸，而产品里没有任何披露

【实测·浏览器】D1 表的场景 ① → ②：**`D = H = 147`、`f = 1.75`、体积校核"充足"逐位相同**。
【实测·Node】`runRiser` 直调（球铁 / cyl / 真实件 HR4012 口径 77.56 kg）：

| Mc (mm) | 仅模数要求 D | **实际输出 D** | final_f |
|---|---|---|---|
| 5 | 33 | 106（**未收敛**，`volOk=false`） | 3.55 撞顶 |
| 8 | 53 | **144** | 3.00 |
| 11.43 | 75 | **144** | 2.10 |
| 20 | 132 | **144** | 1.20 |
| 30 | 198 | 198 | 1.10 |

⇒ **Mc 从 8 到 20（+150%），冒口直径一位没变。** 这复现并扩展了 V2.0-01 的 P0-1
（【上游报告】该报告测得交叉重量约 7.5 kg、恒等式 `冒口重/铸件净重 = shrink/eff` = 21.4%）。

**产品侧的问题不在"体积主导"本身（那是工艺定义），而在没有任何地方告诉用户这件事。**
设计中心结果页给的是「所需补缩金属量 327.72 cm³（铸件净重 77.56 kg ÷ 固态密度 7.1）」——
**数据都在，但没人说"所以 Mc 在本次计算里没有起作用"**。

**【源码确认】设计中心缺失这条披露**：`riser.note.volSimplified`
（「本体积校核按单冒口对整体铸件补缩的工程简化方法计算…」）**只渲染在独立计算器**
（`riserView.js:254`），设计中心**从不渲染它**（只有多热结时的 `res.riser.multiNote`）。

### 🟡 D4 —— 多热结：N 个冒口各自按「整件补缩量」校核

【上游报告】V2.0-01 实测 HR4012 三热结全勾选 → 冒口总重 **50.30 kg = 铸件净重的 64.9%**。
【源码确认】`calcManifest.js:255-259` 逐个 `runOne(p.mc)`，闭包里的 `cast_wt` 是**同一个整件值**，
全仓库无任何分摊逻辑（已用 `castWt /`、`cw /`、`/ items.length` 等模式全仓检索）。
**已有披露**（`:263-265` 的 `multiNote` 明说"V1 不做 feed-zone 分区补缩，各冒口独立校核"），
但披露不等于工程上成立——它仍是一个需要裁决的问题。

### 🟡 D5 —— 三个入口的 `cast_wt` 口径不一致

| 入口 | UI 字面 | 实际传入口径 |
|---|---|---|
| 设计中心 | 「铸件净重（补缩金属量）」（`calcManifest.js:159`） | **净重**（`geometry.netWeightKg`） |
| 独立计算器 | 「铸件重量（体积校验用）」（`riserView.js:50`） | 未标净/毛，默认 10 kg |
| **向导** | 「**⚖️ 单件毛重**」（`wizard.js:235`） | **毛重**（`wizard.js:398 cast_wt: state.partWt`） |

【源码确认】向导把**毛重**直接当"要补缩的金属量"用，与设计中心定稿的净重口径冲突。
毛重 ≥ 净重 ⇒ 向导的冒口**偏大**。本项目无测试覆盖向导这一路。

### 🟡 D6 —— `f` 的步长量化使直径对 Mc **非单调**

【实测·Node】同上表：Mc = 14 → D = 147；Mc = 20 → **D = 144**。
**机制**：`D = round(6·Mc·f)`，`f` 只能取 `1.10 + 0.05k` ⇒ 网格步长 `= 0.3·Mc`。
Mc=14 时步长 4.2 mm（第一个 ≥ 体积需求的网格点是 147），Mc=20 时步长 6 mm（正好落在 144）。
⇒ **把 Mc 改大，冒口反而变小 2%。** 量级小（≤1 个步长），但用户会认为软件坏了。

### 🟡 D7 —— 来源行在多热结分页上用「数值差」判用户输入

【源码确认】`resultsCenter.js:111` `Math.abs(it.hsMc − it.Mc) > 1e-9`
⇒ 用户勾选后把 Mc 改回**恰好等于检出值**时，会被显示成「STL 热结检测」。
与 `calcManifest.js:262` 的 `edited` 是同一个写法（06A1 §6.5 已登记，未统一）。

## 4.5 核查清单逐条回答（116.txt 第三步 A~D）

> 下列每条都指明证据类型；**没有证据的一律标"未证实"**。

### A 几何及输入

| 项 | 结论 |
|---|---|
| STL 单位是否正确识别/转换 | **无自动识别。** `designCenter.js:98` `UNIT_SCALE = {mm:1,cm:10,m:1000,inch:25.4}`，`state.unit` 默认 `'mm'`，用户可在参数区改。STL 若实为 inch 而用户没改，尺寸/体积/重量整体差 16387 倍且**无任何提示**。【源码确认】 |
| 铸件体积是否异常 | `computeVolume` 对**缠绕不一致不鲁棒**（实测翻转 50% 时掉到 8.9%），`validateMesh` 只报 warning 不阻止。方向：体积偏小 ⇒ 冒口偏小。**真实件 HR4012 恰好带 `INCONSISTENT_WINDING`，其体积误差至今无独立真值复算**。【上游报告】+【未证实】 |
| 输入缺失 / 默认值误用 / 单位不一致 | **有三处**：① 向导传**毛重**当补缩金属量（D5）；② `calcManifest.js:246` 在净重缺失时**静默回落**到 `blankWeightKg`（毛重）—— 又一处净/毛混用；③ 设计中心默认 `shape='cyl'`（14%，最低档）、`hd_ratio` 硬编码 1.0、`eff` 不可调。【源码确认】 |
| 热点数量/位置/模数是否显著影响最终尺寸 | **分两种情况**：模数主导区 → 线性（`D = 6·Mc·f`）；**体积主导区 → ≈ 0**（D3 实测 Mc 8→20，D 恒为 144）。 |

### B 公式及数据流

| 项 | 结论 |
|---|---|
| 所需冒口模数的公式与系数 | `Mr_need = Mc × f`，`f` 从 1.10 起、+0.05/轮、上限 50 轮。**`f` 不是安全系数**，是"为满足体积条件被迫放大的倍数"。【源码确认】+【上游报告】 |
| 模数 → 直径/高度换算 | `DfromM` 解析式；`hd = 1` 时圆柱 `M = D/6` ⇒ `D = 6·Mr`。`H = round(D·hd)`。**hd=1 时 `cyl` 与 `sphere_head` 的直径完全相同**（`tests/phase78_test.mjs:131` 已把该现象写成断言：「h/d=1 时各形状同模数 → 直径相同（模数公式等价，非 bug）」），只有补缩效率不同。 |
| 不同冒口形式是否用不同公式 | 是，4 种见 `riser.js:27-63`（`sphere_head` 的 `DfromM` 是不动点迭代 20 次）。 |
| 重复放大 / 系数叠加 / 不必要余量 | **有 4 处**：① `f` 起点 +10% 模数（≈ +33% 体积）；② 体积校核（量级最大）；③ `Math.round(D)`；④ `modOk` 的 0.99 取整容差。**没有任何证据表明其中哪一项"多余"**，本阶段不做这种判断。 |
| 体积校核与模数校核是否分别检查不同约束 | **是**，两条独立约束，`modOk && volOk` 才 break（`riser.js:112`）。 |
| 是否存在"某项通过但其他关键约束未验证" | **是**：`volOk` 只用**整件**缩量，`modOk` 只用 `Mc`，**没有任何一项校核涉及"该冒口实际负责的补缩区"**（D4），也没有"冒口自身收缩 `Vr×εv`"（PHASE 28 P2-1，方向使冒口偏小）。 |

### C 工程假设

| 项 | 结论 |
|---|---|
| 有明确依据/验证记录的 | `RISER_EFF`（《铸造手册》）、形状模数公式（《铸造工艺学》）、`neck_k`（56 审计 ASM/Karsay 印证 0.67~1.1）、`shrink`（企业值，PHASE 28.7-A 人工批准） |

## 5. 只是风险 / 未经证实的假设

| # | 项 | 状态 |
|---|---|---|

## 6. Mc 的不确定性具体影响哪些下游结果

| 下游 | 关系 | 在**体积主导区**的实际影响 |
|---|---|---|
| 冒口直径 D / 高度 H | `DfromM` **线性 ∝ Mc** | **≈ 0**（被体积约束顶住，见 D3） |
| 冒口颈 `d_neck` | `round(4 × Mc × neck_k)`，**1:1** | **仍然线性受影响**（颈不受体积校核约束）⇒ 体积主导时**颈会偏小** |
| 冷铁默认壁厚 | `mc × 2` | 线性受影响（但冷铁未接入主流程，见收尾清单 §D） |
| 冒口检测 1.2 判据 | `ratio = M_riser / Mc` | Mc 偏低 ⇒ ratio 虚高 ⇒ 偏"合格"（06A1 已加确认位） |
| 体积校核 | **与 Mc 无关** | 唯一不受影响的一环 |

> ⚠ **一个本次新注意到的组合**：体积主导时 `D` 与 Mc 脱钩，但 **`d_neck = 4·Mc·neck_k` 仍然跟着 Mc 走**。
> 即"冒口很大、颈很小"这种组合在物理上是自洽的（大冒口小颈 = 补缩通道受限），
> 但它意味着**用户改 Mc 时只改颈、不改冒口**——这一点界面完全没有说明。

## 8. 唯一最优先建议

> **下一阶段最应该先处理的问题是「冒口结果卡在当前状态下会给出与事实不符的确定性」，因为它是本阶段唯一同时满足"有真实浏览器实测证据 / 影响工程判断 / 不改任何工程数值 / 小范围可修"的问题。**

它是**同一个病的三个症状**，都在结果卡上：

1. **场景②** 说「✅ 可直接采用」——事实：Mc 是未确认的自动值，且 06A1 的提示被吞掉了（D1）
2. **场景③** 说「来源：STL 热结检测 Mc = 20 mm…自动估计值」——事实：20 是用户自己填的（D2）
3. **所有重件场景** 不说「本尺寸由体积校核主导、与 Mc 无关」——事实：Mc 从 8 改到 20 尺寸一位不变（D3）

三条合起来就是一句话：**用户在当前界面上无法判断"我这次看到的结论到底算不算数"。**
这恰好是 V2.0 从 06A → 06A1 → R1 一路在解决的问题，而 D1/D2 是它漏掉的两个出口。

### 为什么现在处理它

- **0 行工程数值改动**：`Mc`/`D`/`H`/`d_neck`/`f`/`volOk`/阈值 1.2 全部不动，
  只改 `level`、`note`、一行来源判定 ⇒ **不可能破坏任何模型的计算结果**。
- **可验证**：`tests/experiments/phasev2007_ui_probe.mjs` 已经把三个场景跑通，
  **改完重跑同一个探针即可比对**（浏览器断言，不是字符串匹配）。
- 它挡住了后面所有事：在"结论算不算数"没有答案之前，谈 D4 的分摊、D5 的口径统一都没有意义。

### 为什么不是其他问题

- **不是 D4（多冒口 N 倍）**：它影响尺寸更大，但它**需要工艺裁决**（各冒口是否分摊补缩量），
  是工程决策不是代码任务；而且它**已经有披露**（`multiNote`），危害小于"假 ✅"。
- **不是 D3 的"改体积校核对象"**：那是 V2.0-01 §12.2 的三个工艺裁决之一，**未裁决前不能改公式**
  （116.txt 也明令"不要直接把系数调小"）。本建议只做 D3 的**披露**部分。
- **不是 R2（缠绕污染体积）**：缺独立真值，"未证实"，属于要收集数据而不是写代码。

### 如何验证修复有效

1. 重跑 `node tests/experiments/phasev2007_ui_probe.mjs`，断言：
   - 场景② **不得**出现「✅ 可直接采用」；须出现「🟡 需人工复核」+ 未确认提示；
   - 场景③ 的来源行**不得**出现「STL 热结检测」；
   - 场景①②③ 的 `D`/`H`/`f` **逐位不变**（证明只动了确定性，没动数值）。
2. 新增 Node 侧结构守卫（照 06A1-R1 的做法）：勾选路径与单热结路径必须走**同一个**
   `level`/`note` 口径函数。
3. 全量回归 `node tests/runner.mjs` 必须仍是 **696 通过 / 1 失败**，
   且唯一失败仍是既有的 `phase24 T5`（见 §9）。

> **先查过会不会撞到既有断言**：`grep -rn SAFE_TO_RECOMMEND tests/` 只有 4 处，
> 其中 `phase716_test.mjs:203` 那一条属 **NO_HOTSPOT** 场景、`phase285_test.mjs:276` 直测
> `reliabilityLevel` 纯函数、`phasev2006a1_test.mjs` 两处测的是自动分支与冷铁。
> **没有任何测试断言勾选路径的 `level`** ⇒ 该修复不会撞到既有断言，
> 同时说明**这条路径一直是测试盲区**（这也解释了为什么它能活到 06A1 之后）。

### 什么情况下应该暂停修复、转而收集工程数据

- 如果要动的是 **D4 分摊** 或 **R1 铸铁 `shrink`** —— 先停，去拿
  「1~3 个有企业实际冒口设计的真实件」（实际 D/H、材质、净重、出品率、是否缩孔）。
  没有这个基准，任何数值改动都不可验证（V2.0-01 §12.1 已列，至今未拿到）。
- 如果 `|ΔD| ≤ 1mm` 这类门禁在真实件上被证伪 —— 停，先解决 R2（体积真值）。
