## 2. 状态字段设计及兼容性依据（126.txt §二.4/§二.5）

### 2.1 设计：状态与归因分离 + 文案单一来源

```
calcs/riser.js            converged: boolean          ← 状态（本次新增；= 循环里那个局部变量的原值）
                          bind: 'start'|'modulus'|…    ← 归因（一字未改）
        │
        ▼
js/views/riserStatus.js   riserConverged(r)  → boolean|null   状态判定（含旧结果回退）
                          riserWarning(r)    → {key,params}|null  未收敛警告（按约束分档）
                          fillWarning(w)     → string          导出报告（中文单语）本地填充
        │
        ├─→ resultsCenter.js    tr(w.key, w.params)
        ├─→ reportGenerator.js  fillWarning(riserWarning(r))
        ├─→ riserView.js        tr(w.key, w.params) / fillWarning(...)
        └─→ wizard.js           fillWarning(riserWarning(r))
```

**为什么新增一个模块而不是塞进现有文件**（`js/views/riserStatus.js`，**无 import、纯函数**）：

1. **单一来源**：V2.0-08 的教训原文就写在 `resultsCenter.js` 里 ——「两处各写一份正是 D1 那类漂移的温床」。
   四个入口各写一份未收敛文案，**必然漂移**（本阶段的缺陷③正是这么来的）。
2. **不能放进 `calcs/riser.js`**：UI 文案需要 `tr()`，而 `calcs/` 是纯计算层，**不得依赖 i18n**。
3. **不能放进 `reportGenerator.js`**：导出报告是**中文单语**（其余文案全部硬编码中文），
   而结果卡是双语 ⇒ 两者需要的渲染形式不同。
4. **符合既有惯例**：`js/views/` 下已有 `numcheck.js` / `exampleTag.js` / `nextSteps.js` 等小工具模块。

### 3.3 ★ 附带修掉的一个真缺陷：无效输入会抛异常【实测·生产 + 源码】

`runRiser` 的原顺序：

```js
const sd = RISER_SHAPES[input.shape];
const hd = parseFloat(input.hd_ratio) || 1.0;
const eff = (parseFloat(input.eff) || RISER_EFF[sd.effKey]) / 100;   // ← 未知 shape 时 sd 为 undefined，这里先炸
const cw = parseFloat(input.cast_wt) || 0;
if (Mc <= 0 || !sd) return null;                                      // ← 守卫来晚了
```

**实测**：`runRiser({ shape: '不存在的形状' })`（未显式传 `eff`）抛
`TypeError: Cannot read properties of undefined (reading 'effKey')`，
**而不是返回文档承诺的 `null`**。

**修法**：把 `if (Mc <= 0 || !sd) return null;` 前移到 `sd` 解引用之后。
**数值零影响**（合法输入下 `sd` 恒存在，`hd/eff/cw` 的计算顺序不变；非法输入本来就该返回 `null`）。
**为什么算本阶段范围内**：126.txt §四.6 明确要求"对无效输入进行测试，确保 INVALID/BLOCK 状态**不会被误显示为普通成功结果**"
—— 一个**异常**比"误显示"更糟：它会让调用方整个渲染挂掉。同 PHASE 73 已有的除零守卫属同一类。

## 8. 后续 `D_req` 与真实铸件验证建议（126.txt §六.8）

### 8.1 `D_req`（体积所需直径）—— 建议**下一步做**，但本阶段不做

V2.0-14 §5.3 已给出解析式并在实测上验证（`D_req = ∛(needVol / eff / (π/4))`，夹具实测 **143.91mm**，
与 N=800 时 D 饱和值 144 吻合）。**建议的呈现方式**：

> ⚠️ 未收敛：体积校核未通过。**满足体积校核所需的最小直径约为 ⌀144 mm**（当前 ⌀106 mm，缺口 1.4 倍）。
> 或：增设冷铁 / 改用发热保温冒口（当前补缩效率 14%）后重新评估。

**为什么价值高**：用户现在只知道「不足」，不知道「差多少」；中位缺口 **0.132 倍**（V2.0-14 §4.2）
意味着**多数情况差的不是一点点**，给出数字能让"加大冒口"这个建议变得可判断。
**为什么现在不做**：126.txt §三 明确「本阶段暂不增加 D_req」；且它涉及**新数值输出**，
应当独立成阶段、独立回归。

### 8.2 真实铸件验证 —— ★ 建议**优先于**任何进一步的算法调整

**这是整条 V2.0 线最大的空白**（V2.0-14 已列 P0-2）。具体建议：

1. **需要什么**：**已知合格冒口**的真实铸件若干（含工艺卡上的实际 D/H、材质、浇注温度、
   是否加冷铁，以及**实际是否出现缩孔**）。
2. **怎么用**：把工件的 `Mc`（可从 STL 走现有热点链，或直接取实测热节）与工艺卡的 D/H 对比，
   看现行判据（`Mr_act ≥ 0.99·Mr_needed`、体积校核）**是否与实际结果同向**。
3. **能回答什么**：⌀23 是"偏小到会出问题"还是"只是比原来小但仍安全" ——
   **这是唯一能回答 U-1 的途径**，任何沙箱实验都替代不了。
4. **不能声称什么**：在拿到基准之前，**不得**把"约束都满足"表述成"已通过工程验证"，
   **也不得**把 `bind='limit'` 表述成"真实铸件必然失败"（V2.0-14 §5.5 已定案）。

### 8.3 建议顺序

**P0**：裁决 U-2 的 +1mm → 建立真实件基准（U-1）。
**P1**：`D_req` 披露（§8.1）→ 补 `hd≠1` / 无效输入 / `Mc<0.0833` 的测试（U-5 U-6）。
**P2**：`hotspot_v2` perf 门禁与退出码（U-7，`js/engine` 冻结区，**单独立项**）。

### 8.4 建议**不要**现在做

- ❌ **不要**因为"现在能看见了"就顺手去调 `f` 上限 —— V2.0-14 §5.3 已解析证明 `f_req ∝ 1/Mc`，**方向就是错的**。
- ❌ **不要**动 `js/engine/**`。
- ❌ **不要**在真实件基准到位前重构冒口算法。
