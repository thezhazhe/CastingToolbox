# 两大设想可行性评估

> 2026-08 · 针对用户两个大设想（安卓 APK / 中英双语）的可行性分析
> 评估基于实际代码走查 + 375px 手机视口实测，未做任何改动

---

## 设想一：封装安卓 APK

**结论：可行，是"纯套壳+改 UI"的路子，不用动架构。但 UI 改动量中等偏大，估 2~3 天。**

### 现状实测（375×667 手机视口）

| 检查项 | 结果 |
|---|---|
| `viewport` meta | ✅ 已有（`width=device-width, initial-scale=1.0`） |
| 整体响应式媒体查询 | ❌ 只有 3 个局部 @media（只调内部栅格），**没有整体布局响应式** |
| 移动端首页宽度 | ⚠️ 实际渲染 566px（侧栏 236px 固定不折叠），横向溢出 |
| 移动端计算器页宽度 | ⚠️ 实际渲染 974px，横向溢出严重 |
| 横向滚动条 | ❌ 移动端出现横向滚动 |
| 搜索结果 / 计算表格 | ⚠️ 大表（如 CT 公差表）未做横向滚动容器 |

**根因**：`css/app.css` 第 8 行 `grid-template-columns: var(--sidebar-w) 1fr`，侧栏固定 236px（`--sidebar-w`），主区 1fr。375px 视口下侧栏占满后主区几乎为零，导致整体被撑宽。

### 需要改的 UI（中等偏大）

1. **侧栏 → 汉堡菜单 / 抽屉**：`<236px` 时收起为顶部汉堡，点开滑出抽屉（最核心一项）
2. **顶栏搜索**：375px 下搜索框被压窄，需自适应
3. **工具表单栅格**：`.field-grid2/.field-grid3` 已有 560px 断点，基本够用；但 `.calc-grid`（1.05fr 1fr）和 `.tools-grid` 的 `minmax(300px,1fr)` 需调
4. **大表格**：CT/加工余量等全宽表包一层 `overflow-x:auto`
5. **触摸目标**：按钮/输入最小高度 44px（人因工程）
6. **生产场景条**：chips 需可换行

### 打包方式（可行性高）

- 项目是**纯静态页**（HTML/CSS/JS），WebView 套壳（Android WebView / Capacitor / 简单 APK）直接加载本地文件或 serve.js 即可
- 不用改计算逻辑，纯前端壳
- 风险点：本地文件协议（file://）下 fetch 受限，需内嵌 serve 或打成 WebView 走 http；**此点与 Windows EXE 遇到的问题一致，已有现成解法**（见 [[casting-toolbox-project]] 的 serve.js 模式）

### 建议

- **值得做**，且"先做 UI 响应式"是独立的一步，APK 不做也不亏（Web 版手机访问同样受益）
- 顺序：先做响应式（约 1~2 天）→ 再套壳打包（半天）→ 安卓端适配微调

## 设想二：中英双语

**结论：可行，但现在加入性价比低。核心建议：要么先做"UI 框架级 i18n 预留"（只翻界面、不翻数据），要么等库内容稳定后再整体做。**

### 现状统计

| 项 | 数据 |
|---|---|
| 含中文文件 | 301 个 |
| 总中文字符 | 约 9.7 万 |
| 核心 UI 文案 | 约 1.5 万字，集中在 ~15 个前端文件（各视图 js + index.html + registry.js + scenarios.js + defects.js） |
| 数据层文案 | 约 8 万字，散布在 164 条知识卡 + 30 条缺陷 JSON |

### 分层评估

**UI 层（可行，工作量中）**
- 顶栏加"中 / EN"按钮 → `localStorage` 记忆 → 切 `lang` 类
- 文案抽到字典：视图里的字符串大多是模板字面量，可抽 `i18n(key)` 或建 `lang/zh.js` / `lang/en.js`
- 估 1~2 天做框架 + 首页/顶栏/计算器标题，再 1~2 天铺完所有视图

**数据层（成本极高，不建议现在做）**
- 知识库 164 条内容翻译成英文 = 数万字专业铸造术语翻译，**质量很难保证**（术语错会让老外看错数据）
- 数据层文案不翻，双语的"给全世界用"就是半成品——老外搜到的是中文卡片
- 且**库还在持续扩充**（批B牌号 / 批C型砂 / Campbell 章节），每加一条要翻两份、改两份，维护成本翻倍

### 关键技术点

- 铸造专业术语：shrinker/sand mold/riser/feeding/chill 等，需维护一张术语表，不能机翻硬来
- 单位/格式：mm/Kg/℃ 不变，但说明文字全要翻
- 正则/搜索：`searchKnowledge` 按中文分词，英文要加英文索引

### 建议（二选一）

- **A. 现在只做"UI 壳"**：顶栏语言按钮 + 界面文案中英 + 首页/导航/工具名翻译，数据仍中文，并明示"知识内容中文为主"。工作量可控，给 GitHub 展示加分。**待库稳定后**再翻数据层。
- **B. 暂缓**：等批B/批C 完成、内容不再大改，一次性整体做（UI+数据）。避免翻完又被改。

**我的倾向**：选 **A（先 UI 壳 + 语言按钮）**，理由：① 满足"放 GitHub 给全世界看"的展示需求；② 现在动数据层等于给还在改的内容付双份翻译成本；③ UI 壳做起来独立、可随时扩展。

---

## 一页小结

| 设想 | 可行性 | 工作量 | 建议 |
|---|---|---|---|
| 安卓 APK | 高（纯套壳，不用改架构） | UI 响应式 1~2 天 + 打包半天 | 值得做；先做响应式（Web 也受益） |
| 中英双语 | 高但"现在做性价比低" | UI 壳 2~3 天；数据层翻译另算 | 先做 UI 壳 + 语言按钮，数据层等库稳定 |

**共同点**：两个设想都**不影响现有架构**，都是"加法"。而且**移动端响应式**是 APK 的前提，做了对 Web 手机访问也有好处，**建议优先**。
