## 1. 内浇口面积问题的根因（96.txt §二十三.1）

**根因 ①：`axisAmbiguous`（平板件判据）把大量正常内浇口判成"方向不唯一"→ 截面积留空 → 整个单元掉出总面积。**

判据是 `λ3/λ2 < 0.15 且 λ2/λ1 > 0.5`。第二个条件等价于"**两个大方向相差不到 1.41 倍**"。
而真实内浇口恰恰就长这样：浇口沿铸件边的宽度与砂型里那一段充型路程本来就是同一个量级。

实测（`_p96_probe.mjs`，同一个 20 宽 × 5 厚的截面，只改长度 L）：

| L（充型方向） | 主轴 | 平板判据 | 截面积 | 对不对 |
|---|---|---|---|---|
| 40 | Z ✓ | n | 100.000 | ✓ |
| 30 | Z ✓ | n | 99.900 | ✓ |
| **25** | Z ✓ | **Y** | **null（ambiguous_axis）** | ✗ **整个单元被丢掉** |
| **20** | X | **Y** | **null** | ✗ |
| **16** | X | **Y** | **null** | ✗ |
| **12** | X | n | **60.000** | ✗ 应为 100 |
| 10 | X | n | 50.000 | ✗ |
| 8 | X | n | 40.000 | ✗ |

**两个内浇口只要落在这一带，总面积就会平白少掉 40% 甚至 100%。** 这就是用户报的"总面积仍然偏小"。

**根因 ②：真矩形的形状判定不稳（quadFill 闸门压在噪声带上）。**

`RECT_FILL_MIN` 原先被套在 `QUAD_FILL_MIN ≥ 0.95` 里面。实测**同一块真矩形**的 quadFill：

```
0.9382  0.9439  0.9473  0.9561  0.9605  0.9761     ← 横跨 0.95
（分别来自：eps=0 / pad=10 双件 / res=64 / eps=0.0173 / res=128 / eps=0.11）
```

于是同一块几何**有时判 `rect`、有时判 `irregular`**。而 `sameDims` 要求 `type` 逐字相同 →
两个一模一样的内浇口被判成「多种规格」，主界面也就永远写不出那个尺寸（96.txt §二.1 / §二.2）。

**根因 ③：`sameDims` 要求形状类型完全相同**，把根因 ② 的抖动放大成了"多种规格"。

## 2. 为什么之前两个内浇口总面积会偏小（96.txt §二十三.2）

把三条串起来：

```
两个相同的 20×5 内浇口，充型路程 25mm
  → ① 平板判据命中 → 两个都 null → 总面积 = null（或只算上一个）
两个相同的 20×5 内浇口，充型路程 12mm
  → 主轴取到"宽 20"而不是"充型 12" → 每个只算 5×12 = 60 → 总 120（应 200，少 40%）
两个相同、但网格相位不同
  → ② 一个判 rect 一个判 irregular → ③ 判成「多种规格」→ 主界面写不出 "20 × 5 mm × 2"
```

再加上一个**夹具之外的第四个原因**（保留的既有纪律，未改）：
组件不是闭合实体时拒绝给截面积 → 该单元不计入总和。这在真实 CAD 水密 STL 上基本不会触发，
但程序生成的测试件很容易踩到（交接书 §5.2-7）。

## 5. 梯形测试结果（96.txt §二十三.5）

夹具：上底 10 / 下底 20 / 高 15 的等腰梯形柱，沿 Z 拉伸 30（**几何真值 225 mm²**）。

| 项 | 实测 | 偏差 |
|---|---|---|
| 判型 | `trapezoid` | ✓ |
| 两条平行边 | 19.99 / 10.00 | ≤0.1% |
| 高 | 14.98 | −0.13% |
| 公式值 (a+b)h/2 | 224.637 | **−0.16%** |
| 公式值 vs 实测截面 | 在 `TRAPEZOID_TOL = 5%` 内 | ✓ |

**修了一个显示缺陷**：算法先遇到哪条边取决于切线平面的朝向，原先"上底"报 20、"下底"报 10（对调）。
**这不是算错**（面积与顺序无关），但它会让用户以为模型建反了。
现在两条边按长度排序输出，UI 文案改成「**平行边 a / b · 高 h**」——
切线平面在单元自身的坐标系里切，那里**没有上下**，写"上底/下底"是在陈述一个几何不知道的事实。

## 8. 总面积计算规则（96.txt §二十三.8）

```
totalMm2 = Σ ( 每一个量得出面积的单元 · 它自己那一刀的真实闭合截面面积 )
```

**逐位断言**（96-H）：`k.totalMm2 === objects.reduce((s,o)=>s+o.areaMm2, 0)`（相对容差 1e-12）。

明确禁止、且测试守住的四条：
- ❌ 平均面积 × 数量 —— 96-H 用**不等截面**夹具再证一次（等截面时两者数值巧合相等，证不出东西）
- ❌ 规格尺寸 × 数量 —— 96-I：组"小计"必须等于组内实测之和，不是 `单个面积 × 数量`
- ❌ bbox 面积 × 数量 —— 96-E：半圆截面必须给 157 而不是 200
- ❌ 按分组后的规格重新估算面积 —— 96-I：分组前后总面积逐位不变

量的口径（**未改**，沿用 PHASE 94/95）：垂直于单元主轴、中段 20%~80% 的**中位**截面；
圆形按 πD²/4（D 由实测面积反推，公式值 ≡ 实测值）、矩形按 W×H、梯形按 (a+b)h/2、**异形按实测几何面积**。
前三类都要先过"公式值 vs 实测值"的一致性闸门，过不了就降级为异形。

## 9. 规格分组规则（96.txt §二十三.9）

**两条判据，按"能不能比尺寸"分流：**

| 情形 | 判据 | 容差 |
|---|---|---|
| 两个单元**形状类型相同**且都是 圆/矩/梯 | 逐尺寸比（圆比 D；矩比 W 和 H；梯比两条平行边和高） | `max(0.05 mm, 0.5%)` —— 显示精度与相对量取大者 |
| 类型不可比（一个 rect 一个 irregular）或本身是异形 | 比**实测截面面积** | `1.5%` |

**容差怎么来的（量出来的，不是拍的）：**
- 同一块 20×5×30 的截面，跨网格相位 / 分辨率的实测面积散落在 **99.50 ~ 100.00 mm²**，即离散度约 **0.5%**；
- 真实不同的规格至少差一个可辨认的尺寸档 —— 20 vs 21 就已是 **5%**。

0.05mm / 0.5% 落在离散度之上、真实规格差之下；面积兜底取 1.5%（离散度的 3 倍，真实规格差的 1/3 以下）。
**这三个常数 + 边界用例全部写进测试 96-V**（96.txt §七："必须把这个容差写进测试"）。

**分组的实现纪律**：
- 贪心聚类，按出现顺序，代表值取组内**第一个**单元 → 同样的输入颠倒顺序仍归同一组（96-I 断言）；
- 量不出面积的单元**不参与任何组**（`groupBySpec` 直接跳过），`allSameDims` 要求"所有单元都量出了面积且只有一组"，
  否则一个缺失会被"规格一致"掩盖掉；
- **分组只影响显示**，`totalMm2` 与分组无关（96-I）。

## 11. 参数优先级（96.txt §二十三.11）

96.txt §十三 逐字：**1. 用户本次手动设置 → 2. 当前生产场景 → 3. 项目默认值 → 4. 空值 / 不判定。**
实现为纯函数 `resolveProcessParams()`（`js/model/processInspection.js`），**逐项独立**：

| 情形 | 材质 | 浇注系统类型 | 出品率 |
|---|---|---|---|
| 三项都没设，也没有场景 | `灰铁`（默认值） | `''` 未指定 → **不做速度判定** | 留空 → 用材质表推荐值 |
| 场景设了、用户没动 | 场景值（生产场景） | 场景值（生产场景） | 场景值（生产场景） |
| 用户本次改了材质，别的不动 | **用户值（本次设置）** | 仍是场景值（生产场景） | 仍是场景值（生产场景） |
| 用户把出品率**清空** | — | — | 回落到「默认值 X%」（并把 X 显示出来） |

**两个刻意的判断：**
- `material.yieldSug` 的 `src === DEFAULT` 时**不算**"场景设过"（那只是材料表的 75，不是用户的选择）→ 走默认值这条路，UI 标「默认值 75%」（96-M 断言）。
- **清空出品率 ≠ 手动设了值**：输入框自己的契约就是"留空 = 用该材质的推荐出品率"（占位符与 title 都这么写），
  所以来源必须标回「默认值 X%」。标成"本次设置"同样是假来源（浏览器测试抓到的第二个真缺陷）。

**只读不写**（96.txt §十二末段）：检测中心手动改的一切**只影响本次检测**，一个 `set` 都不调用；
浏览器测试直接读 `localStorage['ct-context']` 验证没有被改（96 §十二 断言）。

## 12. "浇注系统类型"现在到底影响什么（96.txt §二十三.12）

**只影响一件事：要不要拿「企业 R7 参考」比一下平均内浇口速度。**

| 选项 | 值 | 行为 |
|---|---|---|
| **自动**（默认） | `''` | **不做任何速度判定**，只给几何与流量估算 |
| 开放式 | `'开放'` | 启用 `V_LIMIT['开放'] = 1.0 m/s` |
| 封闭式 | `'封闭'` | 启用 `V_LIMIT['封闭'] = 1.5 m/s` |

**它不影响**：截面积怎么量、浇注时间怎么算、流量怎么算 —— 那三样与类型无关，永远照算。

## 18. 当前已知限制（96.txt §二十三.18）

### L1. 充型方向几何上不可判定 —— 主轴是**约定**，不是推导出来的

一个 20×5×12 的长方体内浇口，垂直于「宽 20」切是 60 mm²、垂直于「充型 12」切是 100 mm²。
**两个都是真实的闭合截面，几何本身分不出哪个是"有效流通截面"** —— 要分出来必须知道充型方向。

现在的口径：**取垂直于主轴（即最长方向）的那一刀**。
- 对横浇道、直浇道、以及"充型路程最长"的内浇口，这是对的（而且唯一）；
- 对**充型路程比浇口宽度还短**的内浇口（L=12 < W=20），会切在宽度方向上，面积偏小（60 而不是 100）。
  **这一条本阶段没有修**，因为没有任何几何依据支持"充型方向 = 较短的那条"——
  那样改会让 L=30 的正常内浇口反而算错。

**缓解措施**（本阶段做的）：
- 详细信息表新增「**截面方向**」列（X/Y/Z），每一行都写明这一刀切的是哪条轴，不再是隐藏假设；
- 两个大方向尺度相当（相差不到 1.41 倍）且两条轴切出来的面积**确实不同**（> 2%）时，
  主界面标「⚠ N 个单元截面方向未确认（按最长方向取）」，详情里给出另一条轴的实测面积。

**这是本阶段最需要用户拍板的一条**：如果你的内浇口普遍是"短而宽"，请告诉我，
我们再定一条明确的工程口径（或者做成可按类别指定方向）。

### L2. 组件不是闭合实体 → 拒绝给截面积（保留的既有纪律）

该单元 → `null` + 原因码，**不计入总和**，主界面标「⚠ N 个未计入」，详情表「截面可靠性」列写明原因。
**若再遇到"总面积不对"，请先看这一列**：写着"几何不是闭合实体"就是这条，不是软件算错。

### L3. 没有"一模几件"输入

产品件数 = STL 连通实体数（沿用 89.txt §二）。若一模多件而 STL 只画一件 → 浇注时间偏短（T ∝ √W）。
**待用户裁决**（PHASE 95 就提过，本阶段未变）。

### L4. 工件数量为 0 时仍可算浇注时间

内浇口一个都没导入时，几何检测照给，核心结果里"内浇口总面积 / 平均内浇口速度"留 `—`
并在重点提示里点名原因。

本阶段**没有顺手改**（交接书 §8 P1 第 4 条：建议单独立项）。
