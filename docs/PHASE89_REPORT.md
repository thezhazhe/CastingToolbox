## 2. 为什么这么改

89.txt §十四 的原话是输入区**最终只保留**四件事：① 产品 ② 冒口 ③ 浇注系统 ④ 入口点选，
并明确"不要出现：直浇道导入 / 横浇道导入 / 内浇口导入"。

产品理由是清楚的：用户手上本来就是**一个产品 + 一份工艺**，
让用户自己把一份浇注系统 STL 拆成"直浇道/横浇道/内浇口"三份再分别导入，
是把**程序该干的活推给了人**，而且用户拆出来的往往和几何实际情况对不上。

同时 §四 划了一条红线：**"一个 STL 文件"不等于"程序一定知道每个区域是什么"，
绝对禁止仅凭尺寸、形状或经验规则偷偷把一个几何区域标记为某种工艺语义。**
所以本阶段所有识别都建立在**拓扑与流向**上，没有一条"圆形=直浇道"式的规则。

## 3. Product 多件如何识别（§二）

**纯拓扑，与尺寸形状无关。**

1. `parseSTL` 给出的是**非索引三角汤**（每三角 9 个 float，顶点重复存储），先做**顶点焊接**
   （空间哈希，容差 = 包围盒对角线 × 1e-6）。
2. 按**共享整条边**做并查集（不是共享顶点）——
   两个只在一点相触的实体在工程上就是两件，按共享顶点会把它俩并成一件。
3. 每个连通分量 = 一件，编号 P1、P2、…
4. 总体积 = Σ 各件体积（**只累加可信的**，见下）；总 bbox = 各件 bbox 的并。
5. 只有检测到多件时才显示"件数"，单件不显示"1 件"；**没有"请输入产品件数"输入框**，
   也**不通过复制 STL 人为制造多件**（§二 明令）。

**水密判定**：`boundaryEdges === 0`（没有洞）才算闭合。
不闭合的组件**体积不计入总体积**并标 `volumeReliable=false`（§二："不得假装得到可靠体积"）。

> 实测修正：一开始把"缠绕方向不一致"也算进 `closed`，结果一个普通 100³ 立方体
> 有 750 条方向不一致边（占 16.8 万条的 0.45%），体积却是 998.96（真值 1000，差 0.1%）。
> 两者必须分开：**水密**决定体积可不可信，**缠绕**只是质量提示。

## 4. Gating 如何识别（§四）

用户只导入**一份**浇注系统 STL。程序不假设它里面有什么，先做 §3 的连通分量拆分
（89.txt §十八.5/6：单个连通 / 多个不连通都要正确），
再对每个被点选入口所在的实体做流道追踪。

追踪完全不用"尺寸/形状/经验规则"，只用 §七 优先级里的 ①②③：

| 步 | 判据 | 为什么可解释 |
|---|---|---|
| ① | **拓扑连续性** | 连通分量，纯拓扑 |
| ② | **测地距离场** | 从入口三角形出发在三角形对偶图上做 Dijkstra，边权 = 两三角形质心距 |
| ③ | **分叉** | 沿测地半径推进，看**波前壳层的连通分量数**：1 → 仍在同一根流道；≥2 → 分叉 |

分叉判据是**纯拓扑**的——完全不涉及截面面积、形状、尺寸，
所以不会出现"因为这里比较细就判成内浇口"这种猜测。

**递归分段**（§九：允许一条 / 多条 / **多级**横浇道）：
每一段都问同一个问题"你内部还有没有分叉"。
有 → 分叉前那截是本段主干，分叉后每一支各自继续问；没有 → 本段就是一个末端段。

> 为什么必须递归：一枚内浇口常常是从横浇道上**再分一次**下来的。
> 只分一级的话内浇口会被整条吞进父级里，父级的重心轨迹先沿横浇道走、
> 再拐进内浇口往下去，于是本该水平的横浇道被判成竖直（实测：⌀24 横浇道报成 111 mm²）。

## 5. 多入口如何处理（§五/§八）

- **点几次就有几个入口**：不要求用户输入"直浇道数量"，也不限制数量。
- 每个入口各自建自己的测地场、各自追踪，互不干扰；N 个入口 → N 条候选直浇道。
- UI 只提供 §五 要求的四件事：**当前已选入口数量 / 开始点选 / 结束点选 / 清除入口**，
  另加一个"自动取最上端"作为不想手点时的兜底。没有复杂配置。
- 3D 中每个入口画一个小球 + 法向箭头 + E1/E2 标签。
- **入口落在零面积面片上时自动挪到最近的实体三角形**并记 `entry_snapped`，不放弃该入口。
- **没有入口时**（§十八.14）：浇注系统仍显示组件数 / 总体积 / 三角面等纯几何信息，
  但**不执行**任何需要入口方向的识别。

## 6. 直浇道如何识别（§八）

`depth === 0` 的段 = 从入口到**第一个分叉**之间的那一段。

- 允许 1 / 2 / N 个入口 → 1 / 2 / N 条候选直浇道。
- **不假设截面恒定**。截面形状圆/方/矩/梯形/锥/不规则都无所谓——
  程序从不用任何形状公式，只用实际切出来的面积（§十八.11b 用 40×40 方柱验证了这一点）。
- 多个直浇道：`A_sprue_total = Σ A_sprue_i`。

---

## 7. 横浇道如何识别（§九）

分叉半径以外，按**邻接**分组的各支路，逐个递归。
允许一条 / 多条 / 多级。碎片（小于父段 10%）不当成一条流道。
明显无法判断的复杂区域给 WARNING，不强行分类。

---

## 8. 内浇口如何识别（§十）

**核心判据 = 浇注系统与 Product 的**空间连接关系**，不用"比较薄"这类形状猜测。**

- 对每个**末端段**（含不分叉的直浇道）测"到产品表面的最近距离"；
- 距离 ≤ 判据（件尺寸的 0.2%）→ 这就是与产品相接的那一段 → **内浇口**；
- 判据值在 UI 上明写，不藏着。
- 内浇口允许矩形/梯形/扇形/圆弧/不规则，**不要求用户选形状**。
- **总内浇口面积 = ΣAi（逐个相加）**，绝不使用"平均截面积 × 数量"（§十 明令）。

## 9. 最小有效截面积具体如何计算（§十一/§十二）

这是本阶段最花功夫、也是被实测推翻过最多次的一步。**四道闸门，任一不过就不给数。**

### 9.1 主方向

每段按测地距离排序 → 切 8 个"窗口" → 在窗口重心序列里找**最长的连续共线段**，
弦方向即该段主方向（§十二 明列的「相邻截面中心变化」）。

> **走过的两条弯路（都实测证伪过，代码里留了注释）：**
> ① 用"每个窗口自己求 PCA 主轴"—— 一小段管壁的表面点是个**环**，
>    环的轴向方差 ≈ h²/12、径向方差 ≈ r²/2；只要 h < r·√6，PCA 给出的"主轴"就是**径向**，
>    而且各窗口的径向乱指 → 永远判成"方向不稳"。
> ② 用"相邻窗口流向的夹角"串最长一致串 —— 坏窗口会**一致地歪**
>    （入口端 W0/W1 一起朝同一个歪方向漂），夹角判据根本挑不出来；
>    而且当时那句比较写成了 `winDir[i]` 与 `winDir[i+1]`，i 到 K-2 时越界，
>    导致**每个分段的最后一窗被静默丢掉** —— 而锥形直浇道的细端正好就在那一窗
>    （实测 ⌀40→⌀20 锥：最小截面被报成 406，真值 ~320）。
>
> 共线判据一次覆盖两端（入口端被端面污染、末端被圆角封盖污染），
> 且不含任何"第几窗之后才算数"的经验常数。

### 9.2 有效最小截面

沿该段主方向取 21 个横截面，**只接受同时满足四条**的：

| 闸门 | 判据 | 挡掉什么 |
|---|---|---|
| ① 闭合 | 环闭合 | 网格破口、子集被剪断、切在交汇处 |
| ② 单环 | `loops === 1` | 切面切到了不止一条流道 |
| ③ 形心在中轴上 | 形心到中轴距离 ≤ 0.35×等效半径 | 残缺的月牙环（端部圆角） |
| ④ 非局部突变 | 与左右各两邻点的**中位数**相差 ≤ 35% | 离散化产物 |

再要求有效样本构成**连续的一段**（≥3 个），取其中最小者。

> §十一 的原文要求是"**沿流道主方向**的最小有效截面"，
> 不是"任意方向的最小几何截面"，也不是"整个网格的绝对最小面积"——
> 所以方向由本段主方向决定，不做自由搜索，也就不会有斜切造成的虚假小面积。
>
> 闸门③ 的来历：⌀24 横浇道在离封盖 1.3mm 处切出 **178 mm²**，
> 而它在 0.3mm 外的一整串采样都是 453.7（网格格距 2.3mm，那一刀正好落在被 MC 倒圆的端角上）。
> 闸门④ 的来历同上：锥管的面积本来就在渐变（相邻差 ~4%），
> 拿邻点中位数比才不会把正常的锥度误判成突变。

### 9.3 闸门④（反向验证）

**方向对不对，有一个不依赖任何额外假设的判据：垂直于它切出来的截面，
应当是**一条流道自己的**闭合单环。**
切出来是碎环 → 要么方向不对，要么这一段根本不是一条流道。
两种情况都不该把方向当结论报出去，所以 `axisConfident` **直接绑在截面是否可测上**——
方向由证据背书，不由算法自说自话。

## 11. 哪些情况会 WARNING（§十三/§十七）

**统一只用三种状态：✓ PASS / ⚠ WARNING / ℹ INFO。**
本阶段**没有人为制造任何 PASS** —— 浇注系统侧只报"没算出来"，不报"通过"。

| 码 | 含义 |
|---|---|
| `component_open` | 组件不是闭合网格，体积/截面积可能不可靠 |
| `component_winding` | 缠绕方向不一致（只提示，会让有符号体积有小偏差） |
| `no_fork_found` | 没检出分叉：可能是一根直通流道，或几何过复杂无法可靠分段 |
| `no_product_for_ingate` | 未导入产品：只做纯几何统计，不识别内浇口 |
| `no_gating_product_connection` | 浇注系统与产品没接上（**报出实测最近距离与判据**） |
| `entries_in_different_bodies` | 入口落在互不相连的实体上 |
| `segments_truncated` | 分段数达上限 |
| `entry_snapped` / `entry_out_of_range` / `entry_on_degenerate` | 入口锚点的三种异常 |

截面层面的原因码（UI 显示为"无法可靠计算"而不是数字）：
`open_sections` / `multi_loop_sections` / `empty_sections` / `ambiguous_axis` /
`not_a_duct` / `no_stable_window` / `stable_run_too_short` / `unstable_sections`。

   修法：把查询点**夹到包围盒上**做搜索锚点（不是从查询点自己的格往外扫——
   那样第一圈是球壳，格子数按 r² 增长，实测 cell=3mm、距离 200mm 时
   每点要查 3 万格 × 3000 采样点 = 上亿次 Map 查询，直接把测试跑挂）。

## 15. 当前已知局限

### 15.1 分叉检测在"交汇处几何占比很大"时可能少分一级（**主要局限**）

分叉判据要求壳层的第二分量 ≥ 本层 20%。当交汇处的圆角/焊缝在壳层里占比很大时，
可能**分不出**那一级，结果是一条横浇道把它的内浇口一起吞进去。
**后果**：那一段的主方向会被定到更长的共线子段上（实测一个夹具里 ⌀24 横浇道被判成竖直）。

**但是**：这种情况下截面闸门①（闭合）会失败，UI 显示的是
**"无法可靠计算"**，而不是一个错数。符合 §十三"宁可 WARNING，也不要制造一个漂亮但错误的数字"。

未做的原因：再往下调就变成在一堆合成夹具上调参数，会按下一个坏一个（试过
`forkRatio` 0.2→0.12、`maxAngle`、窗口数 K、偏移裁剪，都是此消彼长）。
**真实 CAD 导出的浇注系统没有尖锐交汇折痕，情况会好得多**；但这需要真实件才能验证，
本轮手上没有可公开的真实浇注系统 STL。

### 15.2 粗网格 / 多零面积面的网格会保守拒绝

实测一份 4 圆柱并集的夹具：3884 个零面积三角形、边界边 0 但缠绕面若干，
此时直浇道段报 `not_a_duct` 而不给数。
零件尺寸跨度大时（夹具坐标范围 320mm 而分辨率固定）⌀30 只剩 5 格，也会拒绝。

**这是设计行为**（§十三），但用户会看到较多"无法可靠计算"。
真实 STL 的网格质量远好于此。

### 15.3 内浇口的位置定义仍是"与产品相接的那一段"

§十 的定义就是连接关系，所以这是对的；但要注意它**不等于**"工艺上那个窄颈"。
若流道与铸件是整段贴合（没有明显缩颈），报出的面积就是那段流道的截面。

### 15.4 其余沿用 PHASE 85~88 的未决项（本阶段**只报告不处理**，§二十）

- Hotspot 真值套件 9/20 的位置定义问题（PHASE 85 的「热点位置」裁决仍未决）

- 新的物理模型 / 凝固模拟 / 缩孔预测

### 15.5 环境事实

## 16. 后续是否需要人工定义

需要，且只有一处是真正卡住能力的：

1. **【需要】"交汇处占比多大才算分叉"这条线**，本质等价于
   "**一段流道从哪里开始算、到哪里算结束**"。
   这不是算法问题，是**工艺定义**问题：直浇道与横浇道的分界，
   在工艺上到底划在交汇圆角的哪一侧？
   定下来之后 §15.1 就能稳定地改；不定的话任何阈值都是在猜。
2. **【可选】"相接"判据的默认值**（现在取件尺寸的 0.2%）。
   本轮给了实测距离，用户可以自己判断合不合理；如需更贴合企业习惯，给一个数值即可。
3. **【可选】有效最小截面的采样密度**（现在每段 21 个截面）。
   段很长时可以加密，但收益远小于第 1 条。

## 17. 结论

> ## **PHASE 89 达到可合并状态。**

理由：

- §一 的七项能力全部**读代码查证**过（不是按文件名猜的），
  其中 `three-mesh-bvh` 的 `intersection.faceIndex` 是个**源码看起来对、实测是错的**坑
  （源码写着 `faceIndex = tri`，实测 60 次射线只有 1/3 对得上原始三角形；
  真正能索引原始 vertices 的是 `face.a / 3`，3/3 命中），已写进代码注释。
- §十八 的 18 项要求**全部有测试**，数值全部对得上解析解（≤0.3%）。
- 回归**零退化**：Hotspot V3 全部指标与 PHASE 85/86/87/88 逐项一致，`js/engine/` 零改动。
- §十三 的第一原则（宁可 WARNING 也不制造漂亮但错误的数字）在实现上是有牙齿的：
  **四道截面闸门 + 方向由截面背书**，算不出就是算不出。
- §二十 的"不要扩大范围"清单**一项都没碰**。

已知局限（§15.1）是**能力边界**而不是错误输出——
越界时给的是 WARNING + 原因，不是错数。
