## §1 当前公式的独立重建（128.txt §三.1~§三.7）

### 1.1 铸件净体积 `Vc` 及其计算来源

【源码】`calcs/riser.js:190`

```js
const Vc = cw > 0 ? cw * 1000000 / rhoUsed : 0;
```

| 项 | 来源 | 语义 |
|---|---|---|
| `cw` | `riser.js:94` `parseFloat(input.cast_wt) \|\| 0` | **铸件净重**，单位 **kg** |
| `rhoUsed` | `riser.js:82` `input.rho ?? md.rho` | **固态密度**，单位 **g/cm³** |
| `md` | `riser.js:81` `RISER_MATERIALS[input.mat] \|\| RISER_MATERIALS.球铁` | 材料表（球铁 `rho=7.1`, `shrink=0.03`）|

**`× 1e6` 是单位换算，不是经验系数**：`1 kg ÷ (1 g/cm³) = 1000 cm³ = 1000 × 1000 mm³ = 1e6 mm³`。
⇒ `Vc` 单位 **mm³**。

【实测·脚本】`cw=77.56` ⇒ `Vc = 10923943.662 mm³` ✓（A3）
**注意**：`Vc` 是**由重量反算的净体积**，代码从不做几何体积积分 —— 名字里的"净"来自
`calcManifest.js:270-275` 的语义约定（用 `geometry.netWeightKg` 而非含加工余量的毛坯重量）。

### 1.2 冒口体积 `Vr` 的计算公式

【源码】`riser.js:133` `Vr = sd.V(D, H)`，`sd` 来自 `RISER_SHAPES`（`riser.js:27-63`）：

| `shape` | `V(D,H)` | 备注 |
|---|---|---|
| `cyl` | `π·D²/4 × H` | |
| `square` | `a² × H` | `D` 即边长 `a` |
| `sphere` | `4/3·π·(D/2)³` | **忽略 `H`** |
| `sphere_head` | `Hc = H − D/2`；`Hc > 0 ? 2/3π(D/2)³ + π(D/2)²·Hc : 2/3π(D/2)³` | 球顶柱；`Hc ≤ 0` 回落为半球 |

### 1.3 体积判据的完整表达式

【源码】循环内 `riser.js:137-141`；最终 `riser.js:193`

```js
const eff = (parseFloat(input.eff) || RISER_EFF[sd.effKey]) / 100;   // :93
const effV = Vr * eff;                                              // :134
const needVol = Vc * md.shrink;                                     // :191
const volOk = cw > 0 ? effV >= needVol : true;                      // :193
```

【本阶段新增·实测】**体积判据没有 `0.99` 松弛** —— 反证：构造 `effV/needVol = 0.3996`
（落在 `[0.99, 1)` 之外但在任何松弛下都应通过）时 `volOk === false`（A3 ✓）。

> ★ **两条判据口径不同**：`modOk ⟺ Mr_act ≥ Mr_need × 0.99`（**有** 1% 松弛），
> `volOk ⟺ effV ≥ needVol`（**无**松弛）。
> ⇒ **`D_req` 的推导中不得引入 `0.99`**，也不得把 `modOk` 的松弛习惯平移过来。

**`cw = 0` 时是"结构性短路"而非算术结果**：`cw > 0 ? … : true` 直接把 `volOk` 钉成 `true`，
而不是让 `effV >= 0` 自然为真。两者在 `cw<0` 时**行为不同**（见 §4）—— 这是本判据最关键的一处细节。

### 1.4 `D_req` 的推导过程

**目标**：求使体积判据成立的最小直径。

```
前提：H = hd · D（高度系数定义）
      Vr = k(shape, hd) · D³                      ← D 的三次齐次式
      effV = eff · k · D³  ≥  needVol
⇒     D ≥ ∛( needVol / (eff · k) )  =:  D_req
```

**`k` 表**（`Vr = k·D³`）：

| `shape` | `k` | 适用条件 |
|---|---|---|
| `cyl` | `π·hd/4` | `hd > 0` |
| `square` | `hd` | `hd > 0` |
| `sphere` | `π/6` | **与 `hd` 无关**（`riser.js:117` 强制 `h = d`）|
| `sphere_head` | `π(3·hd − 0.5)/12` | **仅 `hd ≥ 0.5`**（`hd < 0.5` 见 §3.2）|

**⇒ `D_req` 与 `Mc` 完全无关**（只依赖 `needVol`、`eff`、形状、`hd`）。

### 1.5 变量表（含义 / 单位 / 适用条件）

| 变量 | 含义 | 单位 | 适用条件 / 陷阱 |
|---|---|---|---|
| `cw` | 铸件净重 | kg | `> 0` 体积判据才存在 |
| `rhoUsed` | 固态密度 | g/cm³ | `input.rho ?? md.rho` —— **`??` 只挡 `null`/`undefined`**，`0` 会漏过去 |
| `md.shrink` | **体**收缩率（非线收缩率） | 无量纲 | 球铁 0.03 / 灰铁 0.02 / 铸钢·铝·铜 0.045 |
| `Vc` | 铸件净体积 | mm³ | 重量反算，非几何积分 |
| `needVol` | 需要的补缩体积 | mm³ | `= Vc × shrink` |
| `Vr` | 冒口几何体积 | mm³ | |
| `eff` | 冒口补缩效率 | 无量纲 | `RISER_EFF` 表 / 100；**经验值，无实测标定** |
| `effV` | 有效补缩体积 | mm³ | `= Vr × eff` |
| `D` / `H` | 冒口直径 / 高度 | mm | **整数**（`Math.round`）；`H` 与 `D` 各自独立对同一 `raw` 取整 |
| `hd` | 高度系数 `H/D` | 无量纲 | UI 选项 0.8/1.0/1.2/1.5（`riserView.js:92-97`）|

### 1.6 解析式与现有程序计算的**精确**对应关系

【本阶段新增】程序里的 `D` 是**整数**、`H = round(D·hd)`，而解析式假设 `H = hd·D` 是**实数**关系。
因此**精确判据不是一个闭式，而是一次整数扫描**：

```js
// 精确的"体积所需最小整数直径"（= 未来实现应当采用的口径）
D_req_int(shape, hd, eff, needVol) =
  min { d ∈ ℤ⁺ : sd.V(d, hRound(d)) × eff ≥ needVol }
  其中 hRound(d) = round(d·hd)，sphere_head 再夹取 h ≥ round(d/2)，sphere 强制 h = d
```

**对照结果**【实测·脚本】4 形状 × 6 `hd` × 4 `cw` = **96 组**：

| 关系 | 组数 |
|---|---|
| `D_req_int == ceil(D_req)` | **89** |
| `D_req_int == ceil(D_req) − 1` | **7**（`H` 取整**向上**所致）|
| `D_req_int > ceil(D_req)` | **0** ★ |

★ **`D_req_int` 从不大于 `ceil(D_req)`** ⇒ **闭式不会低估需求**（安全的偏差方向）。
偏差上界 **1 mm**。

**与程序实际 `D` 的关系**：生产 `D` 由 `f` 扫描（`1.10 → 3.55`，步长 0.05）决定，
**不是** `D_req`。
【实测】夹具 `Mc=5, cw=77.56, cyl`：生产 `D=106`（`f=3.55`，`converged=false`），
`D_req_int = 144` ⇒ **差 38 mm**。这正是 `bind='limit'` 的定义。

### 1.7 取整前 / 取整后 / 高度计算的影响

【源码】`sizeAt`（`riser.js:112-126`）：

```js
const raw = sd.DfromM(Mr, hdR);
let d = Math.round(raw);
let h = Math.round(raw * hdR);          // ← 用 raw，不是 d
if (sphere_head) { const r = d/2; if (h < r) h = Math.round(r); }
if (sphere) h = d;
// 模数复核不足 ⇒ d += 1，h = Math.round(d * hdR) 重算
```

【本阶段新增·实测】`D` 与 `H` 是**各自独立地对同一个 `raw` 取整**（A5 ✓）：
`hd=0.8`：`raw=35.750` ⇒ `H=round(28.6)=29`；`hd=1.2`：`raw=31.167` ⇒ `H=round(37.4)=37`。

⇒ **`hd ≠ 1` 时 `D` 与 `H` 可能"错位"**（V2.0-14 §2.10 记录的非单调成因之一）。
**`D_req` 用 `H = hd·D` 的理想关系，天然忽略这层错位** ⇒ 只能作参考值，不能当"该用多大"。

**还有一层**：`DfromM` 本身也不是纯闭式 —— `sphere_head` 用 **20 次迭代**
（`riser.js:44-45`），`cyl`/`square` 才是闭式 `Mr(2+4hd)/hd`。

## §3 `cw = 0` 与 `hd < 0.5` 的分析（128.txt §四.1 / §四.2）

### 3.1 `cw = 0`

| 问题 | 结论 | 依据 |
|---|---|---|
| 数学含义 | **体积约束不存在**：`Vc=0 ⇒ needVol=0`，且 `volOk` 被**结构性短路**为 `true` | `riser.js:190/193` |
| 是否除零 / 无解 / 无限值 | **否**。没有除法用到 `needVol` 或 `Vc` 作分母 | 【源码】 |
| `D_req` 应为多少 | **无定义**（**不是 0、不是 `Infinity`**）| 需求为 0 时"所需直径"没有意义 |
| 应拒绝 / 返回空 / 其他 | **返回"不适用"** | ★ 生产**已有先例**：`yieldPct = Vc > 0 ? … : null`（`riser.js:194`）|

**⇒ 不改变原算法**：`runRiser` 的行为是**正确且有意**的（未填重量 ⇒ 不做体积校核）。
只是未来 `D_req` 必须跟着返回"不适用"，而**不能返回 0**（否则 UI 会显示"⌀0mm"，比不显示更糟）。

### 3.2 `sphere_head` 且 `hd < 0.5`

**（a）退化的具体数学原因**【源码 + 解析】

```
Hc = H − r = D·hd − D/2 = D·(hd − 0.5)
hd < 0.5  ⇒  Hc < 0  ⇒  "球顶柱"的柱体部分高度为负 —— 几何上不成立
```

`k = π(3hd − 0.5)/12` 的分子在 **`hd = 1/6`** 处为零、更小则**为负**：

| `hd` | 0.1 | 0.166… | 0.2 | 0.3 | 0.49 | 0.5 |
|---|---|---|---|---|---|---|
| 闭式 `k` | **−0.0262** | **0** | 0.0262 | 0.1047 | 0.2356 | 0.2618 |

**（b）生产如何处理**【源码】`sizeAt`（`riser.js:116/122`）：
`if (h < r) h = Math.round(r)` —— 把 `H` **夹到 ≥ `r`** ⇒ 实际形状变成「半球（+极短柱）」。

【实测·脚本】`hd ∈ {0.1, 0.2, 0.3, 0.4, 0.49, 0.5}` 全部得到 **`D=34, H=17`（`H/D = 0.500`）**
—— **夹取后实际 `hd` 恒为 0.5**（B3 ✓）。真实 `k = 0.261799 ≈ π/12`。

**（c）能否推导出可靠的替代解析式？**

**能，但有条件**：

```
hd < 0.5 ⇒ H 被夹到 ≥ r ⇒ 有效形状 ≈ 半球 ⇒ k_effective ≈ π/12
⇒ 保守替代式： D_req = ∛( needVol / (eff · π/12) ) = ∛( 12·needVol / (π·eff) )
```

【本阶段新增·实测】**但 `≈` 不能写成 `=`**：夹取是 `H = round(D/2)`，**`D` 为奇数时向上取整**
⇒ 多出一段极短圆柱，`k` **大于** `π/12`：

| `D` | 3 | 4 | 5 | 6 | 7 | 8 | 9 | 11 | 13 | 15 |
|---|---|---|---|---|---|---|---|---|---|---|
| `H=round(D/2)` | 2 | 2 | 3 | 3 | 4 | 4 | 5 | 6 | 7 | 8 |
| 实测 `V/D³` | 0.3927 | 0.2618 | 0.3403 | 0.2618 | 0.3179 | 0.2618 | 0.3054 | 0.2975 | 0.2920 | 0.2880 |
| 相对 `π/12` | **+50%** | 0% | +30% | 0% | +21.4% | 0% | +16.7% | +13.6% | +11.5% | +10.0% |

⇒ **偶数 `D` 时 `k = π/12` 精确成立；奇数 `D` 时偏大**（小直径显著，`D=15` 仍有 +10%）。
【本阶段修正】V2.0-16 §5.6c 写的"`k` 应为 `π/12`"**在偶数 `D` 上正确**，
但**未覆盖奇数 `D` 的取整细节** —— 本阶段补齐。

**（d）结论（不编造补偿系数）**

> **不推导 `hd < 0.5` 的闭式。** 该区间本就"几何不成立"，任何补偿系数都是凭空发明。
> **实现时一律改用 §1.6 的精确整数扫描** —— 它天然覆盖夹取与取整，不需要特判。
> 若必须给闭式，只能用 **`k = π/12` 的保守式**，并**在返回值里声明"保守/上界"**。

**（e）关于"UI 没有该选项 ⇒ 不会被调用"**【128.txt §四.2 明令不得据此认定】

- `hd` 在两个视图里都是 **`<select>`**（`riserView.js:93-97`、`wizard.js:347`），
  选项固定为 `0.8 / 1.0 / 1.2 / 1.5` ⇒ **UI 路径确实只有这 4 个值**；
- 但 `runRiser` 是**导出 API**，`hd_ratio` 是**普通入参**：`wizard.js:373` 自己就是
  `parseFloat(容器取值) || 1` —— **视图层的"挡住"发生在 select 上，不在 `runRiser` 的入口上**；
  测试脚本、`calcManifest` 之外的调用方、将来的批量接口都能传任意值；
- 且 `calcManifest.js:280` **硬编码 `hd_ratio: 1.0`** —— 说明"谁传什么"由**调用方**决定，
  不由 UI 决定。
⇒ **必须在实现层处理，不能靠"UI 挡住了"来免责。**

## §6 建议的未来接口（128.txt §六）

**只提方案，不写生产代码。**

### 6.1 项目既有先例（接口须沿用，而非另立）

| 先例 | 位置 | 可复用的做法 |
|---|---|---|
| `js/views/riserStatus.js` | V2.0-15 新建 | **无 import 的纯函数模块**，作状态的**单一来源**，视图只套容器 |
| `yieldPct` | `riser.js:194` | **"不适用 ⇒ `null`"**（而非 0 / 哨兵值）|
| `mdFellBack` | `riser.js:83` | **静默回退必须带标记**，让消费方能区分"真值"与"兜底值"|

### 6.2 建议结构

```js
// calcs/riserDreq.js —— 纯函数、无 import、不参与 runRiser 的数值路径
export function riserDreq(input) → {
  status,        // 'ok' | 'not_applicable' | 'invalid_input' | 'out_of_range' | 'unreliable'
  value,         // number | null  —— 满足体积判据所需的**最小整数直径** mm（可直接与 r.D 比较）
  continuous,    // number | null  —— 连续解 ∛(needVol/(eff·k))，仅供参考，**不参与比较**
  gap,           // number | null  —— value − r.D（还差多少 mm）；任一侧不可得时为 null
  reason,        // string | null  —— status ≠ 'ok' 时的机器可读原因码
  assumptions,   // string[]      —— 成立前提（见下）
  basis          // { needVol, eff, k, shape, hd, dIntScanSteps } —— 复现所需中间量
}
```

**为什么不复用 `runRiser` 的返回对象**：`runRiser` 的契约是"给尺寸"，本函数是"给差距"。
混进去会让 `runRiser` 多背一个**不参与计算**的输出，违反 V2.0-15 刚立的
「状态与数值分离」原则。**独立模块 = 独立状态域。**

### 6.3 `status` 取值与触发条件（**与 §4 的实测矩阵一一对应**）

| `status` | 触发条件 | `value` | `reason` 示例 |
|---|---|---|---|
| `'ok'` | `cw>0` 且 `Mc>0` 且形状合法 且 `rho>0` 且 `eff>0` 且 全部有限 | 整数 mm | — |
| `'not_applicable'` | `cw` 为 `0` / 缺失 | `null` | `'no_cast_weight'` |
| `'invalid_input'` | `Mc ≤ 0` 或非数值 · 形状非法 · `rho ≤ 0` · `eff ≤ 0` | `null` | `'non_positive_mc'` / `'unknown_shape'` / `'non_positive_density'` |
| `'out_of_range'` | `sphere_head` 且 `hd < 0.5`（闭式不适用）| `null`（或走整数扫描后给值）| `'sphere_head_hd_below_half'` |
| `'unreliable'` | 任一中间量非有限（`Infinity` / `NaN`）| `null` | `'non_finite_amount'` |

**★ 硬约束**（128.txt §六 明令）：
- **禁止**用 `0`、`Infinity`、`NaN` 或"看起来正常的尺寸"表示失败；
- `status !== 'ok'` 时，**`value` 必须是 `null`**，不得是任何数字；
- `gap` 只在 `status === 'ok'` 且当前 `D` 可得时才有值。

### 6.4 `assumptions`（必须随结果一起返回）

```
· H = hd × D 的理想关系（实际 H = round(D·hd)，取整方向可上可下）
· eff 取自 RISER_EFF 经验表，**无实测标定**
· needVol = 铸件净体积 × 体收缩率（线性近似，不含热节位置与凝固顺序）
· value 为**整数扫描**结果，已包含 H 取整与 sphere_head 的 H≥r 夹取
```

### 6.5 不建议做的事

- ❌ **改 `runRiser` 的返回结构**（已冻结的消费面，V2.0-15 刚统一）
- ❌ 在 `riser.js` 里加 `D_req` 字段（会让"给尺寸"的函数多一个"给差距"的输出）
- ❌ 为接口做**大范围重构**（128.txt §六）—— 新模块 + 三个入口各加一段渲染即可

## §7 UI 措辞边界（128.txt §六）

### 7.1 ★ 已有先例：`dModOnly` 的措辞

`js/views/resultsCenter.js:105` 已经这样显示一个**同类参考值**：

> ℹ️ 本尺寸由**补缩体积校核**主导（冒口需承担整件补缩量），改变 Mc 基本不会改变 D/H。
> **仅按模数（Mc × 1.10）所需直径为 ⌀{d} mm。**

**关键在「仅」字** —— 它把该数字限定为"**单看一条判据**的理论值"。
`D_req` 的措辞应**照抄这个模式**：用「仅按…所需」而非「应该用」。

### 7.2 允许 / 禁止

| ✅ 允许 | ❌ 禁止 |
|---|---|
| 「满足当前算法**体积约束**所需的**理论**直径」 | 「保证不缩孔的直径」|
| 「仅按体积校核所需直径为 ⌀{d} mm」（+「仅」字）| 「保证补缩成功的尺寸」|
| 「当前 D 距该值还差 {gap} mm」 | 「已验证的推荐冒口尺寸」|
| 「该值**未考虑**冒口位置、浇注温度、冷铁等实际因素」 | 「按此尺寸开模即可」|

### 7.3 强制提示

凡是展示 `D_req`，**必须同时**满足：
1. 与**当前 `D`** 并列显示（否则用户会把它当成"软件推荐值"）；
2. 出现「**仅**」「**理论**」之一；
3. 当 `status !== 'ok'` 时**不显示任何数字**（只显示"不适用/无法计算"及原因）。

## §9 结论（128.txt §八 A/B/C/D）

### A. `D_req` 在哪些条件下**可以可靠实现**

| 条件 | 状态 |
|---|---|
| `cw > 0` 且有限 · `Mc > 0` 且有限 · `shape` 合法 · `rho > 0` 且有限 · `eff > 0` | ✅ |
| `hd ≥ 0.5`（4 种形状全部）| ✅ |
| `hd < 0.5` **但改用整数扫描**（不用闭式）| ✅ |
| `sphere`（`hd` 无关）| ✅ |

**验证依据**：96 组精确整数解与闭式偏差 ≤1 mm、**从不高估需求**（§1.6）；
齐次性与数值微分双路一致（§5）。

### B. 哪些条件**必须拒绝或返回不适用**

| 条件 | 建议 `status` | 依据 |
|---|---|---|
| `cw = 0` / 缺失 | `'not_applicable'` | §3.1（体积约束不存在）|
| `Mc ≤ 0` / 非数值 | `'invalid_input'` | 生产已 `null`（§4.1 #6-8）|
| `shape` 非法 | `'invalid_input'` | 生产已 `null`（#10）|
| `rho ≤ 0` / 非有限 | `'invalid_input'` | ★ 生产**未处理**（#15/#16）|
| `cw` 为负 / 非数值 | `'invalid_input'` | ★ 生产**未处理**（#3/#4）|
| `hd < 0.5`（`sphere_head`）| `'out_of_range'` **或**改走整数扫描 | §3.2 |
| 任一中间量非有限 | `'unreliable'` | ★ 生产**未处理**（#5/#9）|

### C. 是否需要**调整推导**

**闭式本身不需要调整**（数学与程序一致，§1.6 已验证"从不低估"）。
**需要调整的是实现口径**：

1. ★ **采用整数扫描，而非直接用闭式** —— 闭式忽略 `H` 取整，96 组里有 7 组差 1mm；
2. ★ **`sphere_head` 的 `hd < 0.5` 一律走整数扫描**，**不发明补偿系数**；
3. ★ **`0.99` 不得进入推导**（体积判据无松弛，§1.3）；
4. ★ **`sphere` 的 `k = π/6` 与 `hd` 无关**，不要乘 `hd`。

### D. 是否具备进入下一阶段实现的条件

> **具备。** 但有 **3 项前置条件**：

| # | 前置 | 理由 |
|---|---|---|
| **1** | **先定义退化输入的处置**（§6.3 的 `status` 表）| 生产当前对 8 类退化输入**返回看似正常的结果**（§4.1）。`D_req` 若照抄同样的习惯，只会**再复制一份**这个缺陷 |
| **2** | **明确 §4.3 的 8 项缺陷是否随本阶段一并修** | 它们是 `runRiser` 边界上的既有问题。**修 = 改生产代码**，须单独授权；**不修 = `riserDreq` 必须自己挡在前面**，不能让非法值流进来 |
| **3** | 决定 `D_req` 写在哪（建议**新模块**，**不动 `runRiser`**）| §6.2 |

**⚠️ 但无论是否实现 `D_req`，都不能回答 U-1**（"⌀23/144mm 是否真能补缩"）——
本阶段与 V2.0-16 的结论一致：**只有真实铸件数据能回答**，而 `data/riser-benchmark/` **仍为 0 条记录**。
