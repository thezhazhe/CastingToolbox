## 2. C′ 的生产代码实现及源码位置

### 2.1 新增助手 `sizeAt`（`calcs/riser.js:96-119`，主循环之前）

```js
const sizeAt = (Mr, hdR) => {
  const raw = sd.DfromM(Mr, hdR);
  let d = Math.round(raw);
  let h = Math.round(raw * hdR);
  if (input.shape === 'sphere_head') { const r = d / 2; if (h < r) h = Math.round(r); }
  if (input.shape === 'sphere') h = d;
  const okAt = (dd, hh) => (dd > 0 && hh > 0) && sd.M(dd, hh) >= Mr * 0.99;
  if (!okAt(d, h)) {
    d += 1;                                  // 升一档
    h = Math.round(d * hdR);                 // H 随 D 重算（不是只改 D 这个数字）
    if (input.shape === 'sphere_head') { const r = d / 2; if (h < r) h = Math.round(r); }
    if (input.shape === 'sphere') h = d;
  }
  return { D: d, H: h };
};
```

**调用点**：主循环 `calcs/riser.js:126` `({ D, H } = sizeAt(Mr_need, hd));`
—— 替换原先的 `D = sd.DfromM(...)` / `H = Math.round(D*hd)` / `D = Math.round(D)` / 形状修正 五行。
**取整顺序、`H = round(raw·hd)` 用未取整 D 的既有口径、除零守卫全部保持原样。**

**为什么必须放在循环内**：判定"这一档 f 是否可行"必须用**这一档的真实尺寸**。
放在循环外无法消除抽签 —— 循环仍会因取整丢失而一路走到底（V2.0-12 §7.4 已论证）。

**升档后必然满足**（【解析】）：`round(x)+1 ≥ x ≥ 0.99x`。

### 2.2 未收敛路径还原（`calcs/riser.js:141-155`）

### 3.2 `dModOnly` 裁决 —— **保持纯理论口径，不改数值，不改文案**

**原始定义确认**：`riser.js` 原注释写明「**只按模数（迭代起点 Mr = Mc × 1.10）所需的直径**」，
算式为 `round(DfromM(Mc × 1.10))` —— 即"连续解取整"，**不经过任何校核**。
⇒ 与 124.txt §二 的描述完全一致，**确认是纯理论参考值**，故**保留原算法**。

**"是否需要增加简短说明"的检查结论：不增加。理由三条**：

1. 该字段**只在 `bind === 'volume'` 时渲染**。而在体积主导区 `x = 6·Mr_need ≥ 50`（V2.0-12 律 2），
   取整判据恒真 ⇒ **C′ 永不升档** ⇒ 该区 `dModOnly` 与修复前逐位相同（实测 2202 点全同）。
2. 会出现"升过档"的 volume 点只有 **203 / 5039**，其中 `D − dModOnly ≤ 2mm` 的仅 **12 个**
   ⇒ 理论值与实际值的 ≤1mm 差异，**落在该文案本来就在解释的体积间距之内**。
3. 现有文案本就把该字段限定为「**仅**按模数（Mc × 1.10）所需直径」，并与上句的「**本尺寸**由补缩
   体积校核主导」形成对照 —— **语义已无歧义**。

> ⚠ **为什么不只是"成本考虑"**：改这句中文会连带改动 `tests/phasev2008_test.mjs` 的

### 3.3 `bind` 语义裁决 —— **区分"搜索停止原因"与"工程约束主导原因"**

**从赋值逻辑反推（不靠变量名）**：`prevModOk`/`prevVolOk` 取自**收敛前一轮**（`:134`，仅在该轮未通过时写入）。
故 `bind` 回答的是：**"把 f 退一档（0.05），是哪条约束不让它通过？"** —— 即**"搜索为什么必须前进"**，
是一条**搜索过程归因**，不是纯粹的"约束主导"声明。

| 值 | 判据 | 语义 |
|---|---|---|
| `start` | `prevModOk === null`（**没有上一轮**） | f=1.10 当场双通过 ⇒ **尺寸就是 `Mc × 1.10` 这一步给的** |
| `modulus` | 上一轮**模数**不过、体积过 | 搜索为模数前进 ⇒ 模数把尺寸顶上去 |
| `volume` | 上一轮体积不过、模数过 | 搜索为体积前进 ⇒ 体积把尺寸顶上去 |
| `both` | 上一轮两条都不过 | |
| `limit` | 未收敛 | 不是收敛解 |

`start` 与 `modulus` **都是"模数主导"**（`riser.js:150` 原作者注释：「start —— **模数主导**」）；
区别只在**行走有没有真的发生**。

**C′ 后 `modulus`/`both` 为何不可达**【解析 + 实测】：`sizeAt` 保证**每一档 f** 都满足
`sd.M(D,H) >= Mr_need*0.99` ⇒ `prevModOk` 只会是 `null`（首轮即收敛）或 `true`（上一轮也过），
**永不为 `false`**。而 `modulus`/`both` 都以 `!prevModOk` 为前提 ⇒ **结构性不可达**（数学必然，非实现取舍）。
实测：Mc 1~12 × cw{0,0.5,20,77.56} × {cyl,sphere_head} 全部采样中，`modulus`/`both` **0 次出现**。

**`start` 是否准确表达该用例的新状态**（124.txt §一.3~4）：

- 08-6 的 `mod` 用例 = `riser(2, 0)`。C′ 下它在 **f=1.10 当场双通过**（D=14，`Mr_act=2.3333 ≥ 0.99×2.2`）。
- 尺寸由"Mc × 1.10 这一步"决定 —— **正是 `start` 的定义**。
- **不产生任何用户可见影响**：`bindHint` 对 `start` 返回空串 ⇒ 结果卡一个字都不变。
- ⇒ **确认可采用 `start`，不新增第五种归因值**（124.txt §一.4 未触发）。
