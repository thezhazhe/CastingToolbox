### 2.2 高度重复：212 行 → **96 个独立三元组**

## 3. 差值定义与统计口径

### 3.1 差值方向（131.txt §三 要求先确认）

E3 源码里是 `const diff = dr.value - rr.D`，即：

```
diff = D_req − D_runRiser         单位 mm
      正值 ⇒ runRiser 返回的直径**小于**体积约束所需
      负值 ⇒ runRiser 返回的直径**大于**体积约束所需（体积约束未用尽）
```

PHASE V2.0-19 报告里那句"`limit` 时 runRiser 的 D 比 D_req 平均小 119mm"与 `diff = +119` 是**同一件事**，方向描述正确。

### 3.2 ★ 独立复算（**不复用 E3 的任何函数**）

131.txt §三 明确要求"不要直接沿用未经复核的汇总结果"。`phasev2020_limit.mjs` 重写了网格、差值、判定：

| bind | 组数 | 平均值 | 独立复算 | 一致？ |
|---|---|---|---|---|
| `start` | 79 | −58.4 mm | **−58.42 mm** | ✅ |
| `volume` | 93 | −1.29 mm | **−1.29 mm** | ✅ |
| `limit` | **212** | **+119.2 mm** | **+119.23 mm** | ✅ |

`modulus` 与 `both` 两个取值**在本网格中不出现**（与 V2.0-14 §4.1 的说明一致：`both` 需要 `hd` 偏离到特定位置才可达，本网格的 4 个 hd 值取不到）。

`limit` 组的分布（不只是均值）：

```
min +1.00mm · 中位 +88.50mm · max +397.00mm     （D_req > D_run 的占 100.0%）
```

### 3.3 ★ 均值对"口径"敏感：119.23 还是 94.94

`Mc` 那一维是纯复制，所以行均值把 `Mc` 的权重也算进去了。按 `(shape,hd,cw)` 先求组内均值再平均：

| bind | 行均值 | 去重后均值 | 独立三元组 |
|---|---|---|---|
| `start` | −58.42 mm | −58.41 mm | 63 |
| `volume` | −1.29 mm | −1.43 mm | 82 |
| **`limit`** | **+119.23 mm** | **+94.94 mm** | 96 |

**两个数都成立，口径不同，报告里必须带口径说。** 本节之后一律注明是哪一个。
（差异主要来自 §2.2 那批"Mc 极小 + cw 极大"的不自洽组合集中在 `limit` 组。）

### 4.3 体积缺口的计算公式与单位

本报告用的"体积缺口"是**同一个不等式的移项**，不引入任何新系数：

```
体积缺口 = needVol − effV_run          [mm³]，正 = 不足
  其中  needVol = Vc × md.shrink，Vc = cw × 1e6 / rhoUsed        （calcs/riser.js:276-277，逐字）
        effV_run = Vr(D_run, H_run) × eff                          （calcs/riser.js:209/279）

等价换算（便于工程阅读）：
  "当前尺寸等价可补的铸件重量" = effV_run × rhoUsed / (1e6 × md.shrink)   [kg]
```

### 4.4 ★ 缺口**不是** H 取整口径造成的

`runRiser` 未收敛时返回的 H 用**连续 raw** 算（`riser.js:230`），`D_req` 用 **`round(D·hd)`**（`riserDreq.js:55`）。
先排除"是不是口径差"这一嫌疑：

| 项 | 实测（212 组） |
|---|---|
| 返回 H 与 `round(D·hd)` 的关系 | 相等 180 · **H 更大 32** · H 更小 0（ΔH ∈ {0, 1}） |
| 换成 `D_req` 口径重算体积后 | **仍不足 212（100.0%）** · 变为满足 0 |

⇒ **换口径一个都救不回来。** 缺口是真实的约束不满足，不是浮点/取整假象。

## 5. `bind='limit'` 的返回语义

### 5.1 什么时候产生

`calcs/riser.js:202-220` 的循环：`f` 从 **1.10** 起，步长 **0.05**，最多 **50 轮**，
每轮要求 `modOk && volOk`；50 轮都没同时满足 ⇒ `converged = false` ⇒
`bind = 'limit'`（`riser.js:258`，`!converged` 优先于一切归因）。

撞限时 `final_f` 的**精确值 = `3.5499999999999954`**（0.05 累加 49 次的浮点结果，不是恰好 3.55）。
显示侧 `.toFixed(2)` = `"3.55"`，正确。无实际影响（循环与还原用的是同一个变量），但代码里那个"上限"其实是浮点累加值。

### 5.2 `converged` 与 `bind` 的关系

| 关系 | 实测 |
|---|---|
| `bind === 'limit'` ⟺ `converged === false` | **契约违反 0 次**（384 组） |
| `start` / `volume` 两组 | `converged=true` **79/79、93/93** |
| `limit` 组 | `converged=true` **0/212** |
| 全网格 | `converged=true` **172 / 384**（= 79+93，44.8%） |

`bind` 是**搜索归因**（"为什么必须继续前进"），`converged` 是**状态**。
两者在本阶段实测**完全一致**，未发现矛盾（V2.0-15 的分离是正确的设计，本阶段没有推翻它）。

### 5.3 ★★ 返回的 D/H **不完全等于**循环最后一次尝试的尺寸

`riser.js:228-237` 在 `!converged` 时**把尺寸还原成原取整口径**（撤销 V2.0-13 C′ 的升档）。
实测：

| 项 | 与循环最后一次 `sizeAt` 的一致率 |
|---|---|
| D | **165 / 212**（不同 47，ΔD 恒为 **1**） |
| H | **176 / 212**（不同 36） |

**这不是 bug，是 V2.0-13 有意为之**（"取整补偿只对收敛解生效"，注释见 `riser.js:222-227`）。
但它有一个**未被记录过的副作用**：

> **47 组"模数校核也不过"不是搜索没走到，而是还原把升档撤销了。**
> 实测：在**循环最后一次尝试的尺寸**上，**212/212 全部通过 `modOk`**；
> 到**返回尺寸**上只剩 165/212。**由 ✓ 翻 ✗ 的正好是这 47 组。**

于是 `limit` 组的 `modOk` 分布（本网格）：

```
modOk✓ volOk✗   165 组       modOk✗ volOk✗    47 组
modOk✗ volOk✓     0 组       modOk✓ volOk✓     0 组
```

⚠ **注意不要外推比例**：V2.0-14/15 在另一个网格（26,768 点）上量到的是"`limit` 的 89% 是 `modOk=true`"，
本网格是 **165/212 = 77.8%**。**这个比例随网格变化，不是一个常数**，报告里引用时必须带网格出处。

### 5.4 返回值自洽性（131.txt §三.A3 第 4 问）

384 组**逐位重算**（不看注释，用同一表达式、同一结合次序比对）：

| 关系 | 不一致数 |
|---|---|
| `Mr_act === sd.M(D, H)` | **0** |
| `Vr === sd.V(D, H)` | **0** |
| `effV === Vr × eff` | **0** |
| `modOk === (Mr_act ≥ Mr_need×0.99)` | **0** |
| `volOk === (effV ≥ needVol)` | **0** |
| `needVol === (cw×1e6/rhoUsed) × shrink` | **0** |
| `Mr_need === Mc × final_f` | **0** |

> **⇒ 未发现返回值与 D、H 不一致。** 内部是自洽的；
> §5.3 说的"脱节"发生在**语义层**（返回的数值描述的是还原后的尺寸，
> 而"未收敛"这个判定发生在循环内的另一个尺寸上），**不是数值层**。

| **`rho`** | 用户在项目里显式覆盖过**固态密度**时（`riser.js:167-169`；设计中心在 `solidDensity` 为 USER_OVERRIDE 时会传入） |

⇒ **这 5 条输入路径下的案例，按现有键表无法复现计算结果** —— 而"可复现"是这张表的立表前提（README §E）。
**建议**：在 README §3 键表**补登 5 个键**。**只加键、不改列**，CSV 结构零改动。

**缺口 2 —— 多热结件录不进来**

`resultsCenter` 支持逐热结多块结果（`r.items`，`reportGenerator.js:141-147` 也逐个出警告），
而本表是**一行一案例、单组 `calculated_*`** ⇒ 一个多热结件的多个冒口**无法如实录入**。
**建议**：要么用 `case_id` 后缀（`20260315-01a / -01b`）并在 `missing_data` 写明，
要么新增 `hotspot_id` 列（README §5 规则 7 允许追加列）。

**缺口 3 —— 缩孔**位置**没有结构化字段**

`shrinkage_evidence` 是自由文本。而"缩孔长在**热节处**还是**远离冒口处**"恰恰是判断
"模型偏乐观还是偏保守"的关键（README §8 规则 4 要的正是这个）。
**建议**：**不加列**，在 README §5 规则里要求写明位置即可（成本最低）。

> ⚠ 本阶段**没有**录入任何虚构案例，也**没有**把 §2 的模拟样本计进"真实案例数"。

## 7. 结论、风险和下一阶段建议

### 7.1 对 131.txt §七 六个问题的直接回答

**① 119.2mm 的平均差是否经过独立复算？**
**是。** 不复用 E3 任何函数重写网格与判定，得到 `−58.42 / −1.29 / +119.23`，与 V2.0-19 完全一致。
**但口径要说清**：`+119.23mm` 是**网格行均值**；按 `(shape,hd,cw)` 去重后是 **`+94.94mm`**（96 个独立三元组）。

**② 212 组样本是否为真实生产样本？**
**不是。212 组全部是人工参数扫描，真实生产样本 0 组。**
无 STL、无工艺卡、无浇注记录、无检测结论；网格还把"Mc=0.5mm 配 900kg"这类不自洽组合配在了一起。

**③ 当前 `limit` 返回尺寸有多少比例不满足体积约束？**
**212 / 212 = 100.0%。**
判据取 `runRiser` **自报**的 `volOk`（用**它自己的** D/H/Vr/effV 算出来的，`riser.js:279`），
不依赖任何关于 H 取整口径的假设。换成 `D_req` 口径（`H=round(D·hd)`）复核，**同样是 0/212 满足**。

**④ 是否发现返回值与 D、H 不一致？**
**数值层：没有。** 7 项关系（`Mr_act/Vr/effV/modOk/volOk/needVol/Mr_need` vs `D/H/Mc/final_f`）
在 384 组上**逐位重算，不一致 0 次**。
**语义层：有一处需要写清。** 返回的 D/H 是**还原口径**的尺寸，与循环最后一次评估的尺寸不同
（D 165/212 相同、H 176/212 相同）；`limit` 组里 47 组的 `modOk✗` **正是这次还原造成的**
（在循环最后一次尝试的尺寸上，212/212 都过 `modOk`）。

**⑤ 是否建议进入算法修复阶段？**
**不建议。** 理由见 §7.2。**证据足以证明"问题存在"，但不足以决定"该怎么修"。**

**⑥ 还缺少哪些真实铸件证据？**
见 §6.3 与 §7.3。最要紧的是：**至少一条 `L1` 级别的真实件**——
要么"软件说够、实际缩孔"（模型偏乐观），要么"软件说不够（`limit`）、实际没问题"（模型偏保守）。
README §8 已把这两类写成"真正有信息量的矛盾样本"，本阶段维持这个判断。

### 7.2 结论：问题是什么性质

**主因是搜索空间的结构性不足（不是数值 bug，也不是状态标错）。**

搜索唯一的旋钮是 `Mr_need = Mc × f`，而**体积约束要的那个尺寸与 Mc 无关**。
把"要靠 f 够到体积解"所需的最小倍率记作 `f_req = M(D_req, H(D_req)) / Mc`（纯代数换算，不引入新系数）：

| 统计量 | 实测（212 组） |
|---|---|
| `f_req` 最小 / 中位 / 最大 | **2.88 / 13.13 / 110.7** |
| `f_req ≤ 3.55`（现上限内本可收敛） | **1 / 212** |
| 分布 | `2~5: 21` · `5~20: 112` · `20~100: 70` · `≥100: 9` |
| `D_req / 末次尝试 D` | 中位 **3.74×** · 最大 **35.18×** |

⇒ **抬 f 上限对中位数那一半毫无用处**（要 f≈13，是现上限的 3.7 倍，而更要命的是它本来就不是
"同一个 Mc 下的迭代问题"）。这与 V2.0-13~16 的判断一致，本阶段第一次给出了**数量级**。

次因（次要，但要记录）：**返回值语义有一处未文档化的脱节** ——
`limit` 的 `modOk` 描述的是还原后的尺寸，不是搜索最后评估的尺寸（47/212 因此由 ✓ 翻 ✗）。
这不影响 `converged` 的正确性（**0 组"两条都过却被标未收敛"**），但会让"为什么模数也不过"这个问题
指错方向（读代码的人会以为搜索连模数都没走到，实际上它走到了）。

### 7.3 风险

| # | 风险 | 说明 |
|---|---|---|
| **G-1** | **结论建立在模拟样本上** | 212 组全部是参数扫描。**"100% 不满足体积约束"是模型内部的陈述，不是对真实铸件的陈述。** `volOk=false` 只说明"在软件这套公式里不够"，**不说明真件会缩孔**（README §E 已写明）。 |
| **G-2** | **不知道哪一侧才是错的** | 体积约束本身（`Vc = cw×1e6/rho × shrink` 配手册 `eff` 表）可能是**过保守**的。若如此，"修搜索去够到 D_req"会让冒口**更大** —— 与用户最初报的现象（冒口偏大）**同一个方向**。**修之前必须先知道这一侧对不对。** |
| **G-3** | **不自洽组合放大均值** | §2.2 那批 `Mc≈0.5mm / cw≈900kg` 的组合推高了 `+119mm`。去掉它们后缺口仍是数十毫米量级，但**引用数字必须带口径**。 |
| **G-4** | **`limit` 占比高不等于生产出事** | 本网格 `limit` 占 55.2%，但网格是**刻意构造的**（每个 Mc 配每个 cw），不代表真实使用分布。**真实使用中 `limit` 占多少，现在没有任何数据。** |
| **G-5** | **回归覆盖不完整** | 本阶段浏览器侧只跑了 `browser_v2015_test.mjs`（§5.5）。设计中心结果卡与导出报告两条路径**只做了代码审读**。 |

### 7.4 下一阶段建议（**不自动开展**）

**第一优先：把真实数据补上，而不是先修代码。**

1. **录入 3~5 条真实件到 `data/riser-benchmark/cases.csv`**（人工填写，本软件不代填）。
   优先找**反向案例**：真实缩孔的件，看软件当时判 `modOk/volOk` 是什么。
2. 顺带按 §6.3 补 README §3 键表（5 个键）—— **只改文档，不改 CSV 结构**。
3. 拿到真实件后，**先看 `bind='volume'` 那一组**（V2.0-19 实测它与 `D_req` 只差 1.29mm），
   那是最容易判断"谁对"的一组。

**若之后确要进入修复阶段，需要先补齐的测试（131.txt §三.A4 第 5 问）：**

| 需要的测试 | 为什么 |
|---|---|
| **`limit` 返回值的契约测试** | 钉住"返回的 D/H 是还原口径还是循环末次口径"，以及 `converged`/`bind`/`modOk` 三者在 `limit` 下的**联合语义**。现在这层语义只写在注释里。 |
| **真实件基准的录入校验脚本** | 现在只有 README §7 一条"列数检查"命令行。缺 `case_id` 去重、`evidence_level` 取值、`actual_*` 与 `calculated_*` 不得互相顶替的机器校验。 |
| **`limit` 占比的真实分布统计** | 现在只有刻意构造的网格。需要真实使用分布才知道这个问题**值不值得修**。 |
| **`design_center_test` / `browser_dc_715` 纳入本主题的回归** | §5.5 的两个未跑路径。 |

**明确不建议的方向**：直接把 f 上限从 3.55 调大（§7.2 已量化：中位要 13.1，且方向本身可疑）；
直接把 `D_req` 接进流程（G-2 未解决）。
