## 2. 出品率 78 → 68 的根因（97.txt 输出 4 / §二）

### 结论：**这条链上代码没有 bug。78 进来就是 78。**

我把整条链逐段实测了（浏览器里写真实的 `ct-project` / `ct-context`，整页重载，读 UI）：

| 场景 | `ct-project.material.yieldSug` | UI 实际显示 |
|---|---|---|
| 场景 1 | 78（`USER_OVERRIDE`） | 输入框 **78**，来源 **生产场景** |
| 场景 2 | 78（`SCENARIO`） | 输入框 **78**，来源 **生产场景** |
| 场景 3 | 没有 `ct-project` | 输入框空，来源 **默认值 65%**（球铁材质表值） |
| 场景 4 | 有项目但没有 `yieldSug` 字段 | 输入框空，来源 **默认值 65%** |
| 场景 5 | 78 → 进一趟设计中心 → 回检测中心 | 输入框 **78**，来源 **生产场景** |

**全代码库里根本没有任何地方能产出 68**（`MATERIALS` 的 `y_sug` 是 75/65/58/80/62；
`calcs/yield.js` 里的 68 是**出品率区间**的下界，不是"默认出品率"，而且检测中心不读那张表）。

### 真正的原因：**我自己的测试数据不一致**

- `scripts/browser_inspection_test.mjs` 里我写的是 **78**；
- PHASE 96 的截图脚本 `_p96_shots.mjs` 里我写的是 **68**（当时随手填的）；
- 而 PHASE 96 报告 §10 贴的是**截图的 68**、§15 的测试表写的是**78** —— 两份产物并列展示，看起来就像"78 变成了 68"。

**处置**（97.txt §二.4："如果代码没有 bug，只是测试报告/测试数据错误，则只修正测试"）：
截图已按 78 重新生成，报告口径统一为 78。**没有为了"让数字一致"去改任何产品代码。**

### ★ 但顺着这条链查出了一个**真的**出品率 bug（已修）

追查过程中用浏览器实测发现：**在设计中心改「材料大类」，会把用户手填的出品率无条件抹掉。**

```
用户把「预估出品率」改成 78（src = USER_OVERRIDE）
  → 改材料大类为「灰铁」 → yieldSug 变成 75
  → 再改回「球铁」       → yieldSug 变成 65
  → 工艺检测中心读到：输入框空、来源「默认值 65%」
```

**病灶**：`js/views/designCenter.js` 的 `applyMaterialDefaults()` **无条件**写
`material.liquidDensity / yieldMin / yieldMax / yieldSug / solidDensity`，
而它的**孪生函数** `applyFamilyDefaults()`（就在它上面几行、干同一件事）一直带着
`!isUserSetPath(path)` 守卫 —— 一个有一个没有。
更糟的是被改写的值 `src` 变成了"由材料表派生"，于是工艺检测中心的**来源标签也跟着变**，
用户看到的是"我设的 78 不见了，而且它说这是默认值"。

**修法（1 行，不重构）**：给 `applyMaterialDefaults` 补上同一个守卫。
改完之后实测：78 → 灰铁 → 78；78 → 球铁 → 78；检测中心读到的仍是 **78 / 生产场景**。
**没被用户设过的**参数（密度、出品率区间）照常随材料联动，语义不变。

> ⚠ 这条**不在** 78→68 那条链上，是我追查时在同一条数据链的**上游**发现的。
> 97.txt §十五 说"除非测试证明直接相关，否则禁止顺手修改 Design Center" ——
> 我用浏览器实测证明了它**就在** `ct-project.material.yieldSug → 检测中心` 这条链上，
> 且 §二.3 授权"如果代码存在真实 bug，修复最小范围代码"。改动是 1 处守卫，可随时回退。

## 3. 连接面识别的实际规则（97.txt 输出 3 / §四~§十）

### 3.1 只做一件事：找出"这个内浇口跟谁连着"

```
内浇口（单个组件）
   ↓ ① 逐三角形质心到目标网格求距，≤ tol 的记为"近"
   ↓ ② 近三角形按**共享顶点**并查集聚成连成一片的区域
   ↓ ③ 取面积最大的那块 = 连接区域
   → connectionNormal / connectionArea / connectionCenter（§六：到此为止）
```

目标顺序（§五）：**产品** 优先；识别不出来再退 **横浇道 → 直浇道 → 冒口**。

**没有**用"最近的一个三角形"（§五 明令禁止）—— 必须是**多个相邻三角形连成一片**。
实现上直接复用 `meshComponents.triangleComponents`（焊接 + 并查集），不新写一套。

### 3.2 方向的确定与方向统一

`flowDirection = 连接面法向`（§七）。法向的**朝向**不依赖面片缠绕方向（CAD 与 MC 都可能不一致），
而是用一条纯几何事实定：**法向必须背离内浇口自身的质心**（= 朝外）。
产品端的"朝外"就是"金属离开内浇口进入铸件"的方向 ✓；
只有横浇道端时，"朝外"指向横浇道，所以要**取反**。

### 3.3 三级置信（§八）

| 状态 | 条件 | directionSource | 行为 |
|---|---|---|---|
| **CONFIRMED** | 产品端 + 上游端**都**找到，且两端方向**基本反向**（夹角 > 150°）、两端**确实分开**（> 0.2×内浇口对角线） | `connection` | 用连接方向 |
| **INFERRED** | 只找到一端（产品端，或只有上游端） | `product-connection` / `runner-connection` | 用连接方向 |
| **UNCERTAIN** | 没有可靠连接区域，**或两端方向明显不一致**（§十） | `principal` | **完全退回 PHASE 96**（主轴 + `axisUncertain` + `altAreaMm2`） |

### 3.4 最关键的一条纪律：**connectionArea ≠ effectiveArea**（§九）

连接面识别**只负责定方向**。面积仍然由"**垂直于该方向的闭合截面**"实测得到 ——
复用 PHASE 96 那套已经验证过的切面机制，绝不允许拿 `connectionArea` 当有效截面积。

**实测证据**（测试 97-H 直接断言）：一个连接截面 20×5 的内浇口，
`connectionArea = 146.5 mm²`（它把"贴在产品上那一小片 + 1mm 带宽的侧面"都算进去了），
而**有效截面 = 100.0 mm²**。两者本来就不同 —— 所以实现里若两者相等，就说明违反了 §九。

### 3.5 阈值（两个工程约定，写在一处）

```
tol = max( CONN_TOL_ABS = 2.0mm ,  CONN_TOL_REL = 2% × 内浇口包围盒对角线 )
```

- 绝对下限 2mm：两个实体在 CAD 里本来是贴死的，但**各自独立面片化**后交界处会差出网格步长量级的缝。
  粗网格（产品 250mm 包络 / res=96 → 步长 2.6mm）缝能到 1~2mm。**取 1mm 时会漏判**
  —— 这是浏览器实测踩到的（产品顶面落在 y ∈ ±1.3mm，内浇口底面在 y≈0，缝 1.3mm）。
- 相对上限：大内浇口用自身尺度的一个小比例更合理。
- 这两个数远小于任何真实的浇道间隙（那至少是一个浇口厚度的量级），不会把"没接上"判成"接上"。

## 5. 顺手修掉的一个性能 bug（`js/model/meshDistance.js`）

**这个是本阶段最有价值的意外收获。**

97.txt §十二 要求局部测试要快。phase97 第一次跑用了 **15 分钟**。
逐层量下来：`resolveIngateDirection` 一个内浇口要 **31 秒**。再往下：

```
distanceToMesh × 51536 次 = 31283ms   ← 单次 0.6ms
```

而手工做同样的事（同一个格子里的 266 个三角形逐个算距离）只要 **7.5µs**。
差了 76 倍。给 `grid.get` 装上计数器，真相出来了：

```
单次查询：grid.get 调用 = 4913 次   ← 整整 17³ 格，一圈不落
```

病灶在 `distanceToMesh` 的收工判断：

```js
found = r;                            // ← 每一圈都无条件改写
if (found >= 0 && r > found) break;   // ← r > r 恒假 → 永远不 break
```

本意（函数自己的注释写着）是"找到第一个非空格后，**再多扫一圈**收工"，
正确写法是 `if (found < 0) found = r;`。改完之后：

```
grid.get 调用 = 27 次（本该如此）
distanceToMesh × 51536：31283ms → 543ms
resolveIngateDirection：31280ms → 181ms      （58 倍）
phase97 局部测试：15 分钟 → 21 秒
```

**数值影响（诚实说明）**：多扫的圈只会**多找到**更近的三角形，所以修前的返回值 ≤ 修后的返回值；
即修前更接近真值，修后是文档里写的那个"可能略大于真最近距离"的**上界近似**。
两者都满足"是真实距离的上界"这一契约，差量以格边长为界。
`phase88~96` 全部 182 条断言**逐条通过**（那几条链正是 `meshDistance` 的主要使用者）。

> ⚠ 这个 bug 是 PHASE 90 留下的，**不是 PHASE 97 引入的**；它一直让每次邻近查询白扫 180 倍的格子。
> 我没有"顺手重构"任何东西，只把那一行改回它注释里写的语义。

## 8. 是否建议进入真实 STL 验证（97.txt 输出 7）

**强烈建议，而且这是本阶段之后最该做的一件事。**

理由：
1. **本阶段的价值全部建立在"连接关系是真的"这个前提上** —— 而这个前提只在程序生成的几何上验证过。
   项目里到现在为止**仍然没有任何真实浇注系统 STL**（全盘搜过，61 个 STL 无一属于浇注系统）。
2. 连接面识别吃的是**真实 CAD 导出的两个实体之间的贴合程度**。程序生成的网格是"包络对齐"的，
   真实 CAD 是"布尔运算切出来的" —— 后者的交界处到底差多少，只有真件能告诉我们。
   §3.5 的 `CONN_TOL_ABS = 2.0mm` 就是被"粗网格的缝"逼出来的，**这个数需要用真件校准**。
3. 这一步会直接决定 PHASE 96 那个"短宽内浇口"限制还算不算限制。

**建议的验证步骤**（拿一套在产的浇注系统 STL）：
导产品 + 三类浇注系统 → 点开始检测 → 看详情表「方向来源」列：
- 写「产品连接面 / 两侧连接面」→ 说明连接识别在真件上成立，对一下面积是否与工艺卡一致；
- 写「主轴（最长方向）」→ 连接没识别出来，**请把这份 STL 留给我**，我按真实贴合情况调阈值；
- 出现「⚠ N 个未计入」→ 看「截面可靠性」列（那是"组件不闭合"，另一条既有纪律）。
